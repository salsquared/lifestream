Visualizer architecture

One shell, many lenses over one database. The world map, the time corridor, the tech tree, and the family trees are all views over the same LIFEstream tables. Selecting something in any view propagates to all the others.

1. The core idea

One Vite + React app that mounts a different visualizer depending on which tab you're on. All four visualizers fetch from the same Hono backend, which fronts the same SQLite database. A small set of zustand slice-stores (selection · filters · save · registry · world) holds shared state — nobody talks directly to anyone else.

Clicking Lazaro in the Family Trees focuses the Time Corridor on his life events, highlights his birthplace on the Map, and dims unrelated tech nodes — without anyone having to wire the views to each other directly. They all just react to the same store. (Selection never filters: it sets primary and a derived glow set, and each view decides what "focus" means for it — see §6.)

2. The data layer (what lives in the DB)

Single SQLite file, accessed through Drizzle. Tables fall into three groups: core (used by every viz), map (used by the Map view + the data pipelines, §3), and timeline (used by Corridor + Tech Tree + Family Trees).

2.1 Core

  • save — a versioned project/snapshot. Every per-save row carries a save_id.
  • tag — global (no save_id). One canonical tag list shared across every save; rename once and every save sees the new name. Keeps timeline membership rules (tag = tech) stable across forks. A canonical vocabulary of ~20–30 tags is seeded before any event is tagged (§7.4); a per-save tag vocabulary is explicitly out of scope for v1. A tag that is still referenced by any event_tag row cannot be hard-deleted — the API refuses, and offers a soft-delete (is_retired) that hides it from the picker without breaking existing assignments or membership rules.
  • event_tag — joins tags to events. Since events are per-save, assignments still scope correctly even though tag definitions don't.
  • manifest — a saved export manifest: a named sequence of (view, scope) pairs (§8.6). Per-save and authored, so it is copied on fork like any other authored table.
Storage conventions (settled once, applied everywhere below).
  • Datetimes are TEXT, ISO-8601, UTC, with the Z suffix — 2042-05-01T00:00:00Z. SQLite has no date type; storing a lexicographically-sortable UTC string means ORDER BY, BETWEEN, and index range scans work directly on the column. There is exactly one timezone in this system and it is UTC. The world is fictional; local time is a display concern the Bible never needs, and admitting a second zone would make when_min <= when <= when_max ambiguous. Anything the UI shows as a wall-clock time (July 10th, 2034, 8:04am) is rendered from the UTC value with no conversion.
  • Ids are TEXT, never INTEGER, and always prefixed — <prefix>_<slug|ulid>: sav_, evt_, char_, loc_, proj_, tl_, grp_, rel_, tag_, mfst_, run_. Rows created by the seed get a readable slug (sav_canon, evt_big_one) so the seed is diffable and URLs are legible; rows created at runtime get a ULID suffix (evt_01J9Z…), which is monotonic and collision-free without a server round-trip. The prefix makes a mis-joined id fail loudly instead of silently matching. There is no save_001-style counter anywhere.
  • country.id is the one id that does not follow the prefix rule — it is an external identifier, not one we mint (§2.4).

2.2 Registry (referenced by both timeline & map)

  • character — Lazaro, X, Ines, Bruce Deng, …
    Lifespan has one authority, not two. lifespan_start / lifespan_end and a birth/death event are the same fact stored twice, so the doc names which one wins: if the character has a linked birth or death event (event_actor.role = 'born' | 'died'), that event is authoritative and the lifespan_* column is a persisted derived cache of its rolled when, refreshed whenever the event is written or re-rolled. For characters with no such event — most of the cast — the column is authored directly and is the only record. Family Trees always reads the column, so a card never costs an extra query; a write-time check flags a column that disagrees with its source event.
  • location — Disaster Ridge, Camp Oasis, Kauai lab, ET1, … When geo-locatable, map_ref_kind + map_ref_value point at a country.id or a grouping.id.
    Renames are an identity chain, not separate places. superseded_by_location_id? links a location to the one that replaced it: COPI → FOB Oasis → Camp Oasis → Oasis City → Star City. Each stage stays its own row (events located there keep their historically correct name), but every view resolves a location to the canonical head of its chain before answering "what happened here" — otherwise "events at Star City" returns a fifth of the site's history and the other four fifths look like unrelated places. The chain is strictly linear (one successor, no merges) and cycle-checked at write time.
  • project — NSPD-51A, Xero, Athena, Aurum, Afterlife. Carries date_start / date_end, so a multi-year programme is a project, never an event (§2.3).
  • character_relation — explicit relationships between characters. v1 scope is family-only (parent-of / sibling-of / spouse-of / clone-of) since that's what the Family Trees view renders. Like relation, each edge is stored once: directional types (parent-of, clone-of) read from→to literally; symmetric types (spouse-of, sibling-of) are stored with a canonical ordering (lower id as from) and the renderer treats them as undirected — no mirror row, no drift. Other types (war-buddy, mentor, antagonist) can be added later without a schema change.
    Sibling edges are normally derived, not stored. Two characters with a common parent-of parent are siblings by construction; the Family Trees layout reads that off the tree. A stored sibling-of row exists only for siblings whose parents are not modelled at all — never both, or the same fact is asserted twice and can disagree.

2.3 Timeline tables

An event is a point in time. Anything with duration lives somewhere else. This is a hard rule, and it is what keeps when_min/when_max meaning "we are unsure when" rather than the overloaded "it lasted this long." A span is a timeline of kind era or thread, or a project (which already carries date_start/date_end). Concretely: "2042 onward" is a thread, not an event; "HV V1–V3, '54–'70" is a project whose milestones (V1 ships, V2 ships, V3 ships) are the events. When the Bible gives a bullet that is really a span, the seed splits it into a container plus its dated milestones.
  • event — the world timeline atom. Carries the fuzzy-date quad when_min / when_max / when_precision / when (below), category (closed enum — see §2.5), tech_lane (only meaningful when category='tech'), location_id, project_id, and the optional narrowing FKs range_before_event_id? / range_after_event_id?.
  • timeline, timeline_parent (DAG), timeline_member (manual roster) — the era/thread model. A timeline now carries a closed kind enum — era | thread | cluster — which is what the Corridor's stratum model reads (§5.2): an era is a bounded span of world history (Pre-Big One, Black Fever Era) and must carry era_start/era_end; a thread is an open-ended through-line that need not be contiguous (the Castañeda family, the fusion lineage); a cluster is a tight local grouping (the Etna disaster and its aftermath). A timeline can also include events via membership_rules (jsonb predicate: by tag / by category / by time range / by location). See §2.6 for how a timeline view is composed at read time and for the exact predicate semantics.
    The DAG root is identified structurally, not by its kind. A save's root timeline — tl_world, the World Timeline — is simply the timeline with no row in timeline_parent. It carries kind='thread' for schema simplicity: the enum is closed, a fourth member would exist for exactly one row per save, and every rule that applies to a thread applies to it. Nothing may infer "this is the root" from the kind; anything that needs the root queries for the parentless timeline. The one consequence that has to be stated where the kind is: the Corridor's thread stratum excludes the root (§5.2), because its members are the entire corpus and a thread is drawn from the extent of its members — rendering it would put one bar across all sixty years behind every real thread.
  • relation — event ↔ event graph. Three types: precedes, partOf, renames. An optional note? carries free text about the edge itself — why A precedes B — which is authored with the edge and has nowhere else to live. Powers the Tech Tree edges directly. Stored once with a canonical direction (precedes from=A to=B means "A precedes B" / "B succeeds A"). Reverse views ("what succeeds X?") are derived at query time against the same row — no mirror records, no consistency hazard.
  • event_actor — many-to-many event ↔ character, with a role text field ("crew", "designer", "victim", "leader", "born", "died", …). Drives cross-view glow ("which characters appear in this event") and powers character-filtered views — but Family Trees doesn't render co-occurrence edges. The reserved roles born / died are what link a character to the events that define their lifespan (§2.2).

Fuzzy dates: the range is primary, the point is a roll

The Bible dates events at wildly different precisions — July 10th, 2034, 8:04am, Late 2035, 2036, ~2050s. The schema stores the range the author actually knows, and derives a single point from it for layout:

  • when_min / when_max / when_precision are the primary representation. The author enters a precision plus a value and the pair is derived from it — year 2036 becomes [2036-01-01T00:01Z, 2036-12-31T23:59Z], Late 2035 becomes a Q4 window, a timestamped event collapses to a one-minute window. when_precision is a closed enum: time | day | month | season | year | decade. when_max >= when_min is a CHECK constraint.
  • when is a persisted derived roll inside [when_min, when_max] — not recomputed on read. This is the column every layout, sort, and camera target uses, and persisting it is what makes node positions stable across reloads and across a shared URL. It changes only on an explicit re-roll action.
  • rollDate() is seeded on the event id, so a re-roll is reproducible and the seed script and the UI editor produce the same point for the same event.
  • Views render by precision, never by the roll. A year-precision event displays 2036; a season-precision one displays Late 2035. Only time precision shows a clock. The rolled when is a positioning value and is never printed as if it were known — printing it would fabricate a datetime the Bible does not contain.
  • The bracket FKs narrow the window; they never source it. range_before_event_id / range_after_event_id are optional: given them, the window becomes [max(when_min, before.when), min(when_max, after.when)]. They cannot be the only input, because their own when is itself a roll — Bible L957 ("2071: Enceladus reaches Etna") was going to be the bracket for L958 ("Late 2071: Ines's first symptoms"), which would have made one guess the foundation of another. Every event has a real window of its own first; brackets only tighten it.
  • Write-time validation: a relation of type precedes from A to B requires A.when < B.when. The API rejects the write otherwise, and a re-roll that would violate an existing precedes edge is rejected with the offending edge named. Without this the Tech Tree can draw an arrow that points backwards in time.

2.4 Map tables

  • country — global, not per-save. Real-world. Keyed by a TEXT id that is a zero-padded 3-character ISO 3166-1 numeric code where one exists, and a namespaced synthetic code where one doesn't (§3.1); carries iso_numeric?, alpha3? (display/debug), name, and geometry_source.
  • country_override — per-save rename of a country (e.g. 840 → "United Earth America").
  • grouping — per-save unified nation. Carries name and color only. Membership lives in grouping_country, not in a jsonb array on this row.
  • grouping_country — per-save join of countries to groupings, with PRIMARY KEY (save_id, country_id). That PK is the invariant: a country belongs to at most one unified nation per save. Verified against the existing data — all 237 codes across the 103 groups in data/map_saves/lifestream_map_v1.json appear in exactly one group, zero duplicates — an invariant a jsonb array cannot express and the database cannot enforce. Clicking a country another grouping already owns is no longer a silent no-op: the editor prompts "Move from <X>?", and the server enforces the same rule with this PK regardless of what the client does.
    An "independent nation" is a country with no row here. There is nothing to seed for it. The 74 "independent" groups in the exported JSON are an artifact of the old app — map/src/App.jsx:146-155 synthesizes them at export time from "every country not in a unified nation", with a hardcoded slate color and an independent: true flag no schema has. They are a projection of country, not authored content, and importing them would turn a derived fact into 74 rows that can drift.
  • grouping_metrics — output of the combine step (§3.3): per-save, per-run combined population / GDP / sector mix for each grouping, summed from its member countries' projected values. PRIMARY KEY (save_id, run_id, grouping_id).
  • nation_horizontal — output of the Megacorp classifier (§3.4): per-save, per-run industry horizontal + score per grouping. PRIMARY KEY (save_id, run_id, grouping_id). The World Map reads it as a color overlay.
  • bf_spread — output of the Black Fever spread simulation (§3.2): infection state per country per timestep. A deliberate stub. Its columns beyond (run_id, country_id, t) and its save-scope are open until the sim is designed (OQ8, §3.6); the row exists in the schema so nothing downstream has to invent a name for it later.
  • country_projection — the per-country projection cache (§3.1): pop / GDP / sector mix per country per year per run. Global and save-independent, because it is computed over real-world countries, not over your groupings.
  • source_series — the raw-fetch cache: one row per (source, country_id, indicator, year, vintage) straight from WPP / WDI / WEO. Global. Without it, "same params ⇒ same output" is false the moment the UN or the World Bank republishes a series — the run ledger would record identical params against silently different inputs.
  • sim_run — the run ledger (§3.5): one row per simulation run (stage, params, upstream run ids, status, timing). Global, with a nullable save_id for the save-scoped stages. Every sim output above carries its run_id, so runs are individually versioned and comparable. Not remapped on fork (§7.1).

Why the run_id is in those primary keys and nothing else about runs is. A primary key is one irreversible line: get it wrong and every downstream row, index, and query has to be rewritten. The run harness — an active-run pointer table, staleness evaluation, retention and pruning, DAG orchestration — is a reversible subsystem that can be added later without touching a single existing row. So we buy the cheap irreversible thing now and defer the expensive reversible one (§3.5).

2.6 Algorithms & utilities

  • resolveTimeline(timelineId, saveId) — Compose the membership event set for a timeline (no live filters — see the split below).
    1. Walk timeline_parent transitively to gather this timeline + all descendants. A visited-set guards against cycles; cycles are also rejected at write time.
    2. For each timeline in that set: union timeline_member (manual roster) with events matching timeline.membership_rules (jsonb). Multiple predicate kinds AND together (byTag AND byCategory AND byTimeRange AND byLocation); within a kind, multiple values OR (any matching tag is a hit).
    3. Return the deduplicated event set sorted by when.
    Memoized per (timelineId, saveId) only — a stable key, so the cache actually hits. Invalidation is coarse: any per-save write drops every cached entry for that save. Re-runs are sub-millisecond at our expected scale (~50–500 events per save). Lives in server/src/services/resolveTimeline.ts. The function is resolveTimeline() everywhere — in this document, in the service module and in implementation.html, which called it resolve() and is being corrected to match. The bare word resolve survives in exactly one place, the endpoint path GET /api/timelines/:id/resolve (§5.2), where it is a URL segment and not an identifier.
  • Filtering is a separate pass, deliberately not in the memo key. The caller's live useFilters state (category chips, tag filter, time range, search) changes on every keystroke/scrub, so baking it into resolveTimeline's key would thrash the cache to near-zero hit rate. Instead, applyFilters(events, filters) runs as a cheap O(n) mask over the memoized membership set — client-side, since the membership set is already in hand. Membership is computed rarely and cached; filtering is recomputed freely and never cached.
  • membership_rules — the four predicates, precisely. All four ship in v1; they are the only reason a timeline can be authored once and stay correct as events are added.
    • byTag: string[] — global tag.ids. An event matches if it has at least one event_tag row pointing at any listed tag. Tag ids are global, so this predicate survives a fork untouched — which is the whole reason tag has no save_id.
    • byCategory: Category[] — matches if event.category is in the list. Closed enum, so a typo is a load-time error rather than a silently empty timeline.
    • byTimeRange: [string, string] — a pair of ISO-8601 UTC instants, both ends inclusive. An event matches if its window [when_min, when_max] intersects the range — deliberately not "its rolled when falls inside", because membership must not change when somebody re-rolls a date. An event we only know happened "in the 2040s" belongs to the Black Fever era whether or not its roll happened to land in 2044.
    • byLocation: string[] — per-save location.ids. An event matches if its location_id, resolved to the canonical head of its rename chain (§2.2), is in the list. This is the one predicate holding per-save ids, which is why the fork has to walk into the JSON (§7.1).
    A timeline with no membership_rules is a pure manual roster; a timeline with rules and no timeline_member rows is purely computed; most real ones are both.
  • rollDate(eventId, whenMin, whenMax) → string — the deterministic point-in-window roll behind event.when. It is seeded on the event id, not on wall-clock randomness, so the same event always rolls to the same instant: the seed script, the UI editor, and a re-roll after an unrelated edit all agree, and a save can be re-seeded without every node in the Corridor jumping. An explicit re-roll passes a bumped nonce (rollDate(eventId + ':' + n, …)) so the author can shuffle a date deliberately without losing reproducibility. The window comes from when_min/when_max, narrowed by the bracket FKs when they are set (§2.3); it is never sourced from the brackets alone. Lives in shared/src/rollDate.ts — under shared/src/, because @shared/* maps to ./shared/src/* and a file directly under shared/ is unreachable by the alias (§4.1) — so the UI editor and the seed script share the same logic, and it is one of the four things with a test (§4.1).
  • Reverse relations. relation stores each edge once with a canonical direction (precedes from=A → to=B means "A precedes B" / "B succeeds A"). Reverse queries — "what succeeds X?", "what is X part of?", "what was X formerly called?" — run as SELECTs against the same row. No mirror records, no consistency hazard.
  • Glow derivation is a memoized selector, not stored state. glow is a pure function of (primary, world, registry) — selectGlow(primary, {events, groupingOf}, {locations, projects}), exact signature in §4.2 — a memoized derived selector that recomputes whenever any of those inputs changes, and never a value written into the store by setPrimary. The distinction is load-bearing: opening a shared URL like ?primary=character:char_lazaro sets primary before the world data has finished loading, so a glow computed once at set-time would be empty forever and nothing would ever recompute it. As a selector, the empty first evaluation is simply replaced the moment useWorld resolves. The per-primary recipe is the §6 table. It is purely client-side, which requires the join ids to already be on the client: each event payload embeds its own actorIds[] / tagIds[] / locationId / projectId, and useWorld holds the hydrated event list plus the groupings and groupingOf, the country → grouping index that replaced their inline country members (§4.2). At ~50–500 events per save that is small enough to hold in memory — no dedicated glow endpoint needed.

Forking a save

The worker behind POST /api/saves/:id/fork, in a single transaction:

  1. Insert a new save row with parent_save_id = :id.
  2. For each authored per-save table (§7.1) copy rows under the new save_id with freshly generated row ids, building an old→new id map per table. Derived tables are not copied at all — the pipeline outputs are recomputed in the child save, which is what stops a fork from producing rows that point at a sim_run belonging to the parent.
  3. Second pass: rewrite the copied rows' references according to the remap manifest below. Not "rewrite the per-save FKs" as a matter of judgement — an enumerated, one-line-per-column list, so a column added later is either on it or is a known omission.
  4. Re-canonicalize symmetric character_relation rows. spouse-of and sibling-of are stored lower-id-as-from (§2.2), and the fork regenerates every id — so a pair that satisfied the invariant in the parent very often violates it in the child. Sort each symmetric pair after remapping. Skipping this makes the CHECK constraint abort the entire fork transaction.
  5. Drop any memo cache keyed on the parent save.
  6. Fork-fidelity check. Before committing: re-resolve every timeline in the parent and in the child, and assert the two produce identical sets of event titles. Titles, not ids, precisely because the ids are supposed to differ. This is the one assertion that catches a missed remap — a broken timeline_member or a byLocation rule still pointing at the parent's locations shows up immediately as a membership set that shrank.

Returns the new save id.

3. Data pipelines (calculators & simulators)

Backend services that share one shape: read data → compute → write a table → feed a view. CLI + API, never the browser. They live here, right after the data layer, because the visualizations consume their output — we want the data pipelines running before we build the views on top of them.

The economic + epidemic work is one ordered chain:

  1. Project per country — project each individual country's metrics from now to the target year (§3.1).
  2. Run the BF sim — Black Fever spreads across the individual countries, using their projected metrics (§3.2).
  3. Combine into nations — sum the projected per-country values into each unified nation, using the manual editor's groupings (§3.3).
  4. Assign megacorps — give each combined nation an industry horizontal from its combined projected profile (§3.4).
Project per country, then combine. A nation's metrics are the sum of its member countries projected individually from now to the target year — we project each country as it stands today, then combine the projections. We never merge countries first and project the blob's development as a unit. Megacorps belong to the combined nation, but that nation's numbers come from the projected individuals. (Whether megacorps really do belong to the combined nation is now itself an open question — OQ10, §3.6.)
DEFERRED §3.2–§3.5 are not buildable yet, and this document should not imply otherwise. Nine of the ten open questions in §3.6 land inside them: the projection method, the sector source, the clustering, the syndicate rule, the scope, the currency base, the data coverage, the BF model family and its save-scope, and run retention. A subsystem with that many unresolved decisions cannot be implemented from this doc — what follows is the shape it will take, not a spec.

What is settled and does ship in migration #1 is the schema seam: sim_run, country_projection, source_series, the run_id in the grouping_metrics / nation_horizontal primary keys, and the bf_spread stub (§2.5). Those are the irreversible parts. The machinery that fills them is deferred until the open questions are answered — §3.1's country identity and topojson decisions are the exception and are settled now, because the Map view depends on them immediately.

The stages are modular. Each one is independently runnable — run a stage alone, run a prefix of the chain, or re-run a single stage in place. They hand off only through their persisted tables — country_projection and source_series (both global and save-independent), then bf_spread, grouping_metrics, nation_horizontal — never through in-memory chaining. So a downstream stage can run against an upstream stage's previously-saved output without recomputing it (run §3.1 once, then iterate on §3.2 alone; or tweak a grouping and re-run only §3.3 → §3.4). Each output is computed_at-stamped and run_id-tagged, so a stage can flag when its inputs are newer than its last run (stale) instead of forcing a full-chain rerun. The harness (§3.5) is what would orchestrate this — and is deferred.

3.1 Shared country data & per-country projection

Everything downstream needs real-world per-country numbers projected forward, so this is the shared foundation: identify each country, fetch + cache its real-world series, and project it individually from now to the target year. Because it operates on real-world countries — not on your fictional groupings — the projection is save-independent: computed once, reused by every save. Both the BF sim and the combine step read these per-country projections out of country_projection.

Country identity — the key has to be total over the author's own data

The base layer is real-world countries (the topojson borders we render + the real stats we pull); all the fiction lives above it — unified nations are groupings, renames are country_overrides. So the base country id is just a join key the UI never shows. The requirement on it is not "what's the nicest standard" but "can it name every member of the world the author has already built" — and a pure ISO-numeric key cannot:

  • data/iso-numeric-to-alpha3.json in this repo contains the entries "GUF": "GUF" and "undefined": "SOL". Neither key is an ISO numeric code. Both are live members of data/map_saves/lifestream_map_v1.json — GUF is in the "Guyana" unified nation, SOL is in the partition. They are not junk to be cleaned up; they are the author's data.
  • world-atlas bundles French Guiana inside France's 250 MultiPolygon, so "French Guiana" has no feature id of its own to borrow.
  • Natural Earth gives Kosovo, Northern Cyprus and Somaliland the id -99 — a single id shared by several distinct polygons.

So the key is TEXT, and it is namespaced: a zero-padded 3-character ISO numeric code where one exists ("004", "250"), and "x:GUF", "x:XKX" where one doesn't. Never an INTEGER — 4 and "004" are different values and every join between them is a silent miss. iso_numeric survives as its own nullable column for the joins that genuinely need it; alpha3 is display/debug only and is not a key (ISO vs World Bank vs IOC variants disagree — DEU/GER, CHE/SUI); name is the default real-world name, taken from the topojson feature's properties.name. The column is called name, not default_name, everywhere.

  • Direct topojson join for the ISO-numeric rows — the world-atlas features key on ISO numeric, so the ~240 ordinary countries need no code lookup at render time. The synthetic x: rows are exactly the ones that do need a lookup, and that is the honest shape of the problem: the majority join directly, the exceptions are enumerated rather than lost.
  • Direct population join — UN WPP publishes by the same numeric (M49) codes; population is the metric we most need, and it lines up for free.
  • Stable under renaming — the id doesn't change when a country is renamed, which matters because renaming is a first-class authored operation here (country_override).

A small static lookup maps iso_numeric → the codes the economic sources need where they differ (World Bank, IMF). This refines — it does not reverse — the 2026-05-28 "canonical key = ISO numeric" decision: the join key is still numeric wherever a numeric exists; the change is that the primary key is a string and is total, and the rows numeric can't name are representable instead of dropped. See the decisions log (§3.7).

Borders: which topojson, and where the France split lives

  • world-atlas@2 countries-50m.json, not world-110m. The 110m build carries ~177 features; the 50m build carries ~240. The author's groupings reference 237 country codes, so 110m cannot draw the world that already exists — roughly sixty of the referenced territories have no polygon in it at all. Resolution is a side benefit; feature coverage is the reason.
  • Vendored, version-pinned, offline. It ships at client/public/topojson/countries-50m.json. Today it is CDN-fetched at runtime (map/src/components/Map.jsx:14) and is not in map/public/ at all, so the current app cannot draw a map without a network. Vendoring also pins the exact feature set the country table was imported from — a silent upstream change to the CDN build would otherwise orphan rows.
  • The France → French-Guiana split is data-layer logic, not an app hack. map/src/components/Map.jsx:27-45 carves French Guiana out of France's 250 MultiPolygon by geographic bounds. That belongs in shared/src/geo/deriveFeatures.ts, runs once at topojson load, and is what produces the geometry_source='derived' rows: "250" keeps geometry_source='feature' with the Guiana ring removed, "x:GUF" gets geometry_source='derived'. The same module owns the ?? strId raw-feature-id fallback at map/src/components/Map.jsx:67-68. Putting it in shared/ means the client renderer, the server-side map export (§8.3) and the import script all derive the identical feature set — three places that would otherwise each need their own copy.
  • The 50m build does not resolve 237 ids on its own — it resolves 235. Verified against the vendored file: it carries 241 geometries but only 235 distinct usable ids. Five features have id: undefined (Somaliland, Kosovo, N. Cyprus, Indian Ocean Ter., Siachen Glacier), and 036 is shared by two features — Australia and Ashmore and Cartier Is. Cross-referencing data/iso-numeric-to-alpha3.json, three codes have no 50m geometry by numeric id at all: 175/MYT (Mayotte, folded into France by Natural Earth), GUF (French Guiana, inside 250), and Somaliland. So deriveFeatures.ts owns three jobs, not one: the France split, the raw-id fallback, and disambiguating the duplicate 036. The last is the dangerous one — a naive id → feature map silently keeps whichever feature it reads second and drops the other, with no error. Reaching the authored 237 requires all three.

The vintage column is what makes "same params ⇒ same output" true: WPP and WDI republish, and a run that silently consumed a new vintage would be irreproducible while its sim_run row claims otherwise.

3.2 Black Fever spread simulation DEFERRED

Runs over the individual countries, before they're combined, using their projected metrics — a country's development level (population at least, likely GDP / GDP-per-capita) drives how fast BF spreads, how it's contained, and the quality of care. Simulate BF moving across the world over time — origin, transmission, containment — calibrated against the Bible's BF-era events. The one pipeline that needs both a new output table and a new visualization.

  • Input — the per-country projections from §3.1 (population at least) as per-country development variables; plus an origin + transmission parameters + an adjacency / travel graph + a time range.
  • Output — bf_spread, a deliberate stub: (run_id, country_id, t, …) is fixed, everything else — the state representation, and whether the table carries a save_id at all — waits on OQ8.
  • Visualization — a time-scrubbing map: drag a time slider, watch the map repaint as BF spreads. Shares mechanics with the parked "UEA Membership Map over Time" (§9) — likely a Map overlay with a time control, or its own animated view.

3.3 Combine into nations (nation-grouping calculator) DEFERRED

Fed by the manual map editor (which countries form each unified nation) and the per-country projections (§3.1). For each grouping, it sums the projected member-country metrics over its grouping_country rows into the nation's combined figures at the horizon. It does not pick members (you do, in the editor) and does not project a combined blob — it combines already-projected individuals.

  • Input — the active save's grouping + grouping_country rows + the per-country projections (§3.1).
  • Compute — sum the projected population and GDP over the grouping's member countries; derive combined GDP-per-capita; build a combined sector mix (GDP-weighted value-added, or a merged export basket / aggregated RCA).
  • Output — grouping_metrics, PK (save_id, run_id, grouping_id), per save. Recompute when a grouping's membership changes in the editor.
  • Visualization — no new view: the Map sidebar reads it for a selected nation, and Megacorp (§3.4) reads it as input.

3.4 Megacorp — industry horizontals DEFERRED

The last economic step, and the payoff. Canon (Bible, "The Tiered Corporate Structure", L232–236): business horizontals were strictly divided among a designated number of mega-corporations based on their host nation's pre-collapse economic standing. So this stage reads each nation's combined 2040 profile (the pre-collapse baseline, §3.1) and hands it the horizontal(s) it dominates. These are the H-Megas (Horizontal Megacorporations). Output is nation_horizontal, which the World Map (§5.1) renders as a color overlay.

CANON The count per nation is fixed by GDP rank tier, and it is deterministic. Bible L232–236:
  • Tier 1 — top-10 GDP nations (US, China, Germany are the named examples): a maximum of a dozen megacorporations, each with absolute monopoly over a specific technological or industrial sector.
  • Tier 2 — rank 10–50: two to five per nation, managing broader manufacturing and service portfolios (the Indonesian conglomerate's 3D-printed organs, the Mexican conglomerate's synthetic skins).
  • Tier 3 — sub-50: exactly one national megacorporation, focused on "the region's most historically successful or resource-rich exports".
This answers half of the old "how is the designated number of H-Megas derived" question (OQ3): the count comes from the host's GDP rank tier, not from the nation count, and it is a lookup rather than a modelling choice. The classifier's job shrinks to producing a GDP ranking and reading the tier off it.

The horizontal taxonomy stays emergent, and canon does not touch it. Canon fixes how many megacorps a nation gets; it never says which industries the horizontals are. Its own examples are sector-derived rather than drawn from a fixed list (Indonesia → 3D-printed organs, Mexico → synthetic skins; Tier 3 explicitly gets "the region's most historically successful or resource-rich exports"). So the clustering is still needed — for which horizontals exist and which nation dominates each, not for how many each nation is allotted. The categories are discovered from the 2040 profiles; the allocation is canon.

  2. Cluster the nations' combined 2040 profiles (sector mix, GDP, GDP-per-capita) → an emergent set of horizontals.

Packaging: the whole chain lives under server/src/services/simulation/ — one module per stage (project · bfSim · combine · classify), named for what it is (a stack of world simulations, not just its last step). Each stage is independently invokable: CLI scripts/simulate.ts <stage|all> and API POST /api/simulation/<stage> run a single stage or the full sequence, with the persisted tables as the hand-off between them. Backs a per-stage "recompute" control in the Map sidebar.

3.5 Run manager (the harness) DEFERRED

The stages (§3.1–§3.4) are modular, but something has to orchestrate them and version their runs — that's the harness. It's a thin layer over the stages, not a fifth stage; the CLI and /api/simulation would go through it.

Two version axes — don't conflate them:

  • Save (§7) — a branch of the authored world: groupings, events, characters. Forking copies authored data.
  • Run — a parameterized execution of a sim stage: a projection method, a BF origin + seed, a target year. A save can hold many runs; you compare them.

What ships now: sim_run exists, every output row carries its run_id, and that run_id is part of the primary key of grouping_metrics and nation_horizontal. That is the whole of the run machinery being bought — and it is bought precisely because a primary key is irreversible.

What is explicitly deferred: the active-run pointer table (which run a view reads by default), staleness evaluation (computed_at comparison against upstream), run retention and pruning, and DAG orchestration. Every one of those is a reversible subsystem: it can be added later without rewriting a row. The rule is buy the cheap irreversible thing, defer the expensive reversible one. Until the pointer table exists, "the active run" is simply the newest sim_run for that (scope, stage), resolved in the query.

Run scope follows stage scope: the source fetch and the per-country projection (§3.1) are save-independent, so their runs are global; the combine (§3.3) and classify (§3.4) are per-save; BF's scope (global over real countries, or per-save) is an open question (OQ8).

3.6 Open questions (projection, combine & megacorp)

  1. GDP projection method. Log-linear on per-capita real GDP × projected pop? ARIMA? Solow-style? Convergence model? Decide after eyeballing the historical series.
  2. Sector source. WDI value-added (coarse, simple) vs OEC/Comtrade RCA (sharp, more ingest work).
  3. Emergent clustering — which horizontals, not how many. How to cluster the 2040 profiles into horizontals: which features, which algorithm, how a nation is judged to "dominate" one. The count half of this question is now closed — canon fixes megacorps-per-nation by GDP rank tier (§3.4), not by the nation count.
  4. Syndicate (S-Mega) formation. Now that syndicates are in scope: what rule stacks H-Megas into S-Megas (and S-Megas into Monolithics)? A later stage in the chain + its own output table + the §9 syndicate map. Note that MEGACORP-the-company sits at this tier, so this stage is where canon's named antagonist has to become representable.
  5. Scope. Compute metrics + horizontals for single-country groupings too, or only multi-country unified nations? (Note that under §2.4 a lone independent country has no grouping row at all, so "single-country grouping" means an explicitly-authored one-member nation.)
  6. Currency / base year for GDP comparisons (constant 2015 vs 2020 USD).
  7. Economic-data coverage for the non-standard territories. Reframed: this was previously filed as a country-identity failure mode. It is no longer that — §3.1 settles representability: every territory the author uses has a primary key, synthetic where ISO has none. What remains, and is genuinely still open, is coverage: WPP/WDI/IMF publish nothing for several of these rows (Somaliland, Northern Cyprus, Western Sahara; Taiwan is missing from IMF; French Guiana is folded into France in most economic series). Options are to impute from the parent territory pro-rata by population, to carry nulls and let the combine step propagate them, or to fall back to a hand-entered figure. Sparse-history small states are the same question in a milder form.
  8. BF run scope. Is the BF sim save-independent (spreads over real countries + global projections) or per-save (calibrated to that save's BF-era canon)? Decides whether bf_spread carries a save_id, and therefore whether it is an authored-adjacent per-save table or a global one.
  9. Run retention. How many runs per (scope, stage) to keep before pruning, and what the default "active run" pointer follows (latest, or pinned). Deferred with the rest of the harness (§3.5).
  10. Do H-Megas attach to pre-merger countries rather than to merged nations? NEW Canon's tier examples are all individual 2025-era countries — US / China / Germany for Tier 1, Bulgaria / Ukraine / Sri Lanka for Tier 3, Indonesia and Mexico for Tier 2 — and the H-Megas form during the Black Fever era while the country mergers complete after it. That ordering cuts directly against the existing decision that megacorps belong to the combined nation, and against §3.3 feeding §3.4. If canon is read literally, the classifier's unit is the country and the grouping only inherits its members' H-Megas. Still open as a canon question — but the schema no longer waits on it (2026-09-02). nation_horizontal is keyed on country_id, the finer grain, so both readings are representable: if H-Megas attach to countries, the rows are already right; if they attach to merged nations, a grouping's horizontals are a rollup over its grouping_country members. The reverse would not have worked — from a grouping-keyed row you cannot recover which member contributed what, so a grouping_id key would have silently answered this question in migration #1. Settling the canon still gates §3.4's logic (which unit the tier allotment counts against); it no longer gates the key.

Toolchain facts, recorded so nobody re-discovers them. These are properties of the shipped root config, not preferences — each one was a build error first.
  • TypeScript is 6.0.3, and baseUrl is a hard error (TS5101) — not a deprecation warning. tsconfig.base.json therefore carries no baseUrl, and its paths are config-relative: "@shared/*": ["./shared/src/*"], "@server/*": ["./server/src/*"]. That relative root is exactly why every shared file sits under shared/src/ above: @shared/rollDate resolves to shared/src/rollDate.ts and to nothing else.
  • The base sets composite: true, which is not a free flag. Every workspace tsconfig has to declare its own rootDir and outDir; declaration: false stops being an override and becomes a hard error (TS6304); and each build writes a *.tsbuildinfo, which is machine-local incremental state and is gitignored.
  • tsx and drizzle-kit live at the root, not in the server workspace — every one-shot script in scripts/ and every npm run db:* runs from the repo root off a single install.
  • drizzle.config.ts is at the repo root and its url is ./data/lifestream.db — not ../data/lifestream.db, which assumed a config living in server/. The path resolves against the config's own directory, so the wrong one does not fail: it silently creates a second, empty database one directory up.
  • Vitest does not read compilerOptions.paths. Alias resolution is not inherited — every alias is mirrored by hand in vitest.config.ts, and the two tables drift silently. tests/smoke.test.ts exists for exactly that: it compares the two and fails the moment they disagree.
Four tests, not a coverage push. vitest at the root, npm test runs it, and exactly four things are tested because exactly four things are both silent when wrong and expensive to discover late: resolveTimeline()'s DAG recursion and cycle detection (an infinite loop or a silently truncated timeline), the fork remap manifest (a missed column produces a fork that looks fine and points at the parent — the fidelity check in §2.6 is this test's runtime twin), rollDate's determinism (a non-deterministic roll makes every reload move every node), and the country import (all 237 codes resolve, the (save_id, country_id) partition holds, the x: rows exist). Everything else is a single-user local tool where the feedback loop is looking at it. The fifth spec in the layout, tests/smoke.test.ts, is not a fifth thing tested — it tests the harness, catching the silent alias drift described above.
The test DB fixture: :memory:, fresh per test file. Each spec opens its own in-memory SQLite database and applies the migrations at setup through the drizzle better-sqlite3 migrator, so no test sees another test's rows and no test touches data/lifestream.db. Vitest's default forks pool already isolates at file granularity, which is the grain this fixture wants — and it stays forks deliberately: better-sqlite3 is a native module and the threads pool goes badly with it.

The binding constraint this places on the server. server/src/db/index.ts must expose a createDb(url) factory (or read its path from the environment) rather than a module-level singleton hardcoded to data/lifestream.db. With a hardcoded singleton, importing anything that reaches the DB opens the real file at import time and both fixture styles are blocked — the fork-remap and country-import tests above cannot be written at all without first refactoring that module. The app's own connection is then one call to the same factory, so there is still exactly one way to open the database.

4.2 Shared state (zustand slice-stores)

Five small slice-stores. Splitting by concern keeps subscriptions narrow — a Tech Tree node doesn't re-render when the save name changes. Every view reads from these and writes to these; nobody talks directly to any other view. The shell owns the fetch: on mount and on every activeSaveId change it loads the registry and the world into useRegistry / useWorld, so a view never issues its own per-save query and four views never race to load the same event list.

// useSelection — what the user clicked on. glow is NOT stored here.

Why glow is a selector and not a value in the store. The old shape had setPrimary compute glow and write it. That is correct exactly once — on a click, with the data already loaded. It is wrong in the case that matters most: opening a shared URL. /v/timeline?primary=character:char_lazaro restores primary during the first render, before useWorld has any events, so the computed glow is empty — and because nothing re-invokes setPrimary when the fetch lands, it stays empty forever. As a memoized selector over (primary, world, registry) the empty first evaluation is simply superseded when the data arrives. The §6 model is unchanged; only where the value lives moved.
Why selectGlow takes two grouped store slices and not a positional list. The earlier (primary, events, groupings, locations) shape cannot compute three of §6's rules, and the reason is a consequence of another decision made in the same pass: groupings carries zero derivable information now that membership moved out of grouping.country_ids and into the grouping_country join table (§3.7, 2026-09-01) — a grouping row is a name and a color and nothing else, so the country rule and the grouping rule both need world.groupingOf, the country → grouping index. A project primary's lead needs registry.projects, which was never passed at all. Grouping the arguments by source store is what stops this churning a third time: the next rule that needs one more field widens a Pick instead of changing the arity at every call site.

The primary + glow split resolves "click event, glow its actors" cleanly: setPrimary({type:'event', id}) records what was clicked, and useGlow() derives the halo from event_actor, location_id, project_id, event_tag. Views read primary to know what was clicked and glow to know what to highlight around it. Neither ever removes anything from a view — that is useFilters' job.

'project' is a real primary and every view answers it. It stays in the union because the command palette already emits it (§4.3) and §6 derives project ids into glow. What each view does: the Corridor focuses the project's linked events and draws its date_start–date_end span as a thread; the Tech Tree glows the tech events carrying that project_id and draws the same span as a lane band (§5.3); the Map glows the locations of those events; the Family Trees glow the project's lead_character_id plus every actor on its events. No view has to render a "project page" — a project is a lens, like everything else.

4.3 View switcher & URL state

Top-bar tabs are enough for v1. Each tab is a route under /v/<view>. Active view is preserved in the URL.

Selection, active save, and filters all serialize to URL search params — e.g. /v/timeline?primary=event:evt_athena_launch&save=sav_canon&cat=tech,disaster&from=2034&to=2050&root=tl_bf_era. For a link to be truly shareable, the filter state has to ride along too — otherwise the recipient sees an unfiltered view at the right selection. Browser back/forward navigates the whole state; reload restores it exactly, and the derived glow catches up when the fetch lands.

Cmd-K opens a command palette that can switch views and jump to entities ("go to Lazaro" → ?primary=character:char_lazaro, "show Project Xero" → ?primary=project:proj_xero). The palette is just another URL writer.

5.2 Time Corridor (3D)

The flagship view: a depth-stratified corridor you fly through, where moving forward moves through time and moving deeper moves through levels of abstraction — from four eras spanning sixty years, down to individual events minutes apart. This section is normative. implementation.html owns the build sequence and cites the contracts below; it does not define them.

The stratum model

The corridor is not one scene at four zoom levels; it is four co-existing Z-planes, each a complete rendering of the same save at a different granularity. Depth is the abstraction axis. Time is the long axis, and it is the same time in every stratum.

  • Era stratum (deepest) — one node per timeline with kind='era', laid out across era_start → era_end. Eras carry explicit bounds precisely so this stratum does not have to derive its extents from member events: an era with no events yet still occupies its span, and adding an event never silently moves an era's boundary.
  • Thread stratum — one ribbon per kind='thread' timeline: the Castañeda family line, the fusion lineage, the Disaster Ridge site history. A thread is drawn from the min/max when of its resolved members; threads are open-ended and need not be contiguous, so a thread renders as a set of segments across the times where it actually has members, connected by a faint continuation line. The DAG root is excluded. The parentless timeline (tl_world) is a kind='thread' row for schema reasons only (§2.3), and its members are every event in the save — so it would resolve to the entire corpus and draw a single bar across all sixty years behind every real thread. The stratum filters it out structurally: threads, minus the timeline with no timeline_parent row.
  • Cluster stratum — tight local groupings like "the Etna disaster and its aftermath". Two shapes feed this stratum, and both render. Most clusters are derived at read time: a shared pure function groups the resolved event set by shared tags and time proximity, so a freshly seeded save — which contains zero kind='cluster' rows — still shows a populated cluster stratum instead of an empty plane. Any derived cluster the author cares about can then be promoted to a stored, editable timeline with kind='cluster', which gives it a name, a description, a color and membership rules of its own. A stored cluster supersedes the derived one over the same events, so nothing is drawn twice — promotion replaces, it does not duplicate. The derivation is one shared function (client, export builders, and any future server-side renderer call the same one), so a cluster never means two different things in two places. This is the stratum that keeps a dense fortnight from collapsing into an unreadable smear at event level.
  • Event stratum (shallowest, nearest the camera) — one node per event row, positioned at its persisted when, labelled by its precision (§2.3). This is the ground truth the other three summarize.

Membership at every stratum comes from the same place: resolveTimeline() (§2.6), memoized per (timelineId, saveId). A stratum never runs its own query and never invents its own grouping rule — if a timeline's contents look wrong in the Corridor, there is exactly one function to look at.

Canonical scale contract NORMATIVE

The event stratum's d3.scaleTime is canonical. All cross-view and cross-jump math — camera fly-to targets, the Tech Tree's shared X axis, viewport clamping — uses it. Other strata render via a z-dependent multiplier applied at draw time only, never in the data model.

This is stated once, here, and everything else cites it. It is what resolves the collision between per-stratum time scales, a single world scale, the viewport clamp, the fly-to target, and the Tech Tree's claim to share the Corridor's scale: there is one scale, and the other strata are renderings of it. A consequence worth stating plainly — no stratum ever stores a position. A node's world-space X is canonicalScale(event.when) * m(z) computed in the render pass; nothing persists it, nothing else reads it, and changing the parallax curve can never desynchronize two views.

Depth: cross-fade, parallax, and no snapping

  • Strata cross-fade; they do not switch. Each stratum has an opacity envelope over camera depth — a plateau where it is fully drawn and a falloff on either side — and adjacent envelopes overlap across a band. Inside that band both strata are partially drawn, so the era ribbon is still faintly visible while the first cluster nodes resolve out of it. There is no depth at which the scene hard-cuts, and therefore no frame where the user loses their place.
  • Each stratum has its own parallax multiplier. The deeper strata compress time (sixty years has to fit on screen) and the event stratum expands it (two events a fortnight apart have to be distinguishable), so each stratum draws at canonicalScale(t) * mstratum(z). Because the multipliers differ, the strata slide past each other as the camera moves — which is exactly the parallax that makes depth legible rather than decorative. The multiplier is a draw-time factor and lives nowhere else: not in the store, not in a payload, not in the URL. A camera target computed in canonical time is correct in every stratum by construction.
  • Depth is continuous. There is no snap-to-stratum. Snapping would mean the camera can never rest in the blended region, which reduces the cross-fade to a transition animation between two discrete states and contradicts the whole point of moving through depth. The scroll/pinch input maps to a continuous z; the strata respond to wherever it lands. Named depths exist only as fly-to targets (a "back to eras" control), never as quantization of the axis.
  • Depth and time are independent inputs. Scrubbing time at any depth keeps the current abstraction level; changing depth at any time keeps the current instant centred. The two never fight, because both are expressed against the canonical scale.

Focus, the viewport stack, and the breadcrumb

Selection sets primary and nothing else (§6). Focus is a separate, Corridor-local concept: which timeline is currently the root of the corridor. It is what turns an infinite scroll into a navigable structure.

  • Focus root — the corridor renders resolveTimeline(root) and its descendants. The default root is the save's top-level "World Timeline". Focusing a narrower timeline (double-click an era ribbon, or pick one from the timeline tray) re-roots the corridor on it.
  • Viewport stack — re-rooting pushes the previous (root, cameraZ, cameraT) triple onto a stack rather than replacing it. Popping restores the camera exactly where it was, not to a default. Without the stack, drilling into an era and coming back out loses the reader's position every time, and the corridor stops being explorable.
  • Breadcrumb — the stack rendered as a horizontal trail in the corridor's chrome (World Timeline › Black Fever Era › Etna). Clicking an ancestor pops to it. The breadcrumb is a view of the stack, never a second source of truth.
  • The root serializes as ?root=<timelineId> (§4.3) and is what scopeParams.rootTimelineId carries into an export (§8.5). The stack itself is session state and is not serialized — a shared link lands the recipient at the focused timeline, with an empty stack, which is the correct behaviour for someone arriving cold.
  • Fly-to — a cross-view jump (§6) animates the camera to canonicalScale(target.when) at the depth whose envelope best contains the target, and re-roots only if the target is outside the current root's membership. Because the target is computed in canonical time, the fly-to lands correctly no matter which stratum was on screen when it started.

Relation arcs and filters

  • precedes renders as an arc from A to B in the event stratum, bowed out of the corridor wall so it reads as a link rather than a collision. Because A.when < B.when is enforced at write time (§2.3), every arc points forward and the direction needs no arrowhead disambiguation.
  • partOf is a containment edge, so at coarser strata the child does not draw its own node — it folds into its parent's, and the parent's node carries a count. This is how the corridor gets quieter as you pull back without anything disappearing arbitrarily.
  • renames draws as a continuity thread between the two events, and is what the Location Life view (§9) would eventually read alongside the superseded_by_location_id chain (§2.2).
  • Filters mask; they never remove. applyFilters (§2.6) runs over the memoized membership set and produces a per-node dimmed flag. A filtered-out node keeps its position and its arcs — it fades. Removing nodes would reflow the corridor on every keystroke and make the time axis lie about density.
  • Glow and filter are visually distinct and orthogonal. Glow is additive (a halo on glow.eventIds); filtering is subtractive (opacity down on non-matches). A node can be both glowing and filtered out, and it should look like exactly that.

Glow does not walk the location rename chain — and the asymmetry with membership is deliberate. An event sited at loc_fob_oasis glows when loc_fob_oasis is the primary and not when its canonical head loc_star_city is: the selector matches event.location_id by equality and never follows superseded_by_location_id (§2.2). The membership_rules.byLocation predicate does the opposite — it resolves an event's location to the head of its chain before testing it (§2.6). That is not an inconsistency to be tidied away later; the two answer different questions. Membership asks "what happened at this place, across its whole history" — a Disaster Ridge timeline that returned only the Star City fifth of the site's events would be wrong, which is the entire reason the chain exists. Glow asks "what is this row attached to" — if clicking the FOB Oasis stage lit up Star City's events too, the five stages would be indistinguishable in every view and there would be no way to inspect one of them. The §9 Location Life view is where the whole chain is shown at once, and it asks for that explicitly rather than getting it by default.
Why this scales. When you add a new view later — Project Gantt, Location Life, Cast Calendar — it only needs to read primary / glow from selection and do its own writes. No edits to Corridor, Map, Tree, or Family Trees. The Map's megacorp-horizontal overlay (§3.4) is the same story: another reader of the same save, wired to nobody.

7. Saves & versioning (DB-backed, app-wide)

Versioning is app-wide via a save table that every visualizer respects. Every editable row in every entity table carries a save_id foreign key. The shell holds an "active save" in state; every API call passes it; every SELECT filters on it. Forking a save (e.g. "branch this into Version 2") inserts a new save row and copies all authored per-save rows from the parent (§2.6).

save {
  id             text          // prefixed id, per §2.1 — "sav_canon", "sav_01J9Z..."
  name           text          // "Version 1", "What if Athena succeeded?", "Movie canon"
  description    text
  created_at     text          // ISO-8601 UTC
  parent_save_id text?         // for forks
  is_archived    boolean
}

7.1 What's in a save

The in-save tables split in two, and the split is what makes a fork correct. Authored rows are things a person wrote and a fork must preserve exactly. Derived rows are pipeline output — copying them would hand the child rows that point at a sim_run belonging to the parent, so they are recomputed in the child instead.

  • In-save · authored (copied on fork): event, timeline, timeline_parent, timeline_member, relation, character, character_relation, location, project, grouping, grouping_country, country_override, event_tag, event_actor, manifest.
    note grouping_country and manifest were both absent from this list entirely. grouping_country copies verbatim in its country_id and remapped in its grouping_id: it is per-save, but country_id points into a global table — the existing verbatim-copy rule survives the country_ids → join-table change word for word.
  • In-save · derived (recomputed, never copied): grouping_metrics, nation_horizontal, and any future pipeline output. A fresh fork simply has no metrics until the chain is re-run for it, which is the honest state — its groupings may already differ from the parent's.
  • Scope open — see OQ8 (§3.6): bf_spread, and nothing else. It is deliberately on neither list above. §2.5 defines it as (run_id, country_id, t, …) with no save_id, and a table with no save_id cannot be in-save — filing it under "in-save · derived" would pre-commit an open decision. OQ8 settles it: if the BF sim turns out to be calibrated per save, bf_spread gains a save_id and joins the in-save · derived list; if it stays save-independent (spreading over real countries and global projections) it joins the shared list alongside country_projection. Either way it is pipeline output and is never copied on fork — only which list it lands on is open.
  • Shared (global, never copied and never remapped): country (real-world borders + default names), tag (canonical tag list), sim_run (the run ledger), country_projection (save-independent projections), source_series (raw-fetch cache).

The exact per-column treatment on fork — remap / verbatim / conditional / json-walk — is the enumerated manifest in §2.6, together with the symmetric-relation re-canonicalization step and the fork-fidelity check.

7.2 Operations

  • GET /api/saves — list
  • GET /api/saves/:id — one save's metadata
  • POST /api/saves — create a blank save. Fork is not an option on this route — there was previously a second, undocumented way to fork here, and two code paths for one operation means one of them eventually skips the remap manifest.
  • POST /api/saves/:id/fork — the only fork path. Copies the authored per-save rows under a new save id, per §2.6.
  • PATCH /api/saves/:id — rename / edit description / set is_archived
  • DELETE /api/saves/:id — soft delete (sets is_archived); hard delete via a separate explicit endpoint, and refused while any other save has this one as its parent_save_id
  • GET /api/saves/:id/dump — emit a JSON dump of every row under this save, for backup / sharing. GET, not POST: it mutates nothing, and being a GET makes it linkable, cacheable and trivially scriptable — which matters because it is the backup path (§7.4). Distinct from /api/export in §8, which renders documents.
  • POST /api/saves/import — load a JSON dump under a new save id

7.3 UX in the shell

Save picker lives in the top bar next to the view switcher. Shows current save name + a dropdown for switching / forking / renaming. Switching saves replays every view's data load — fast because everything is keyed on a single column.

setActive clears primary. Every per-save row id is regenerated by the fork (§2.6), so a primary carried across a save switch points at an id that either doesn't exist in the new save or — worse — belongs to an unrelated row. Clearing primary also clears the derived glow for free, since glow is a selector over it (§4.2); there is no second piece of state to remember to reset. The URL sync writes the cleared selection back, so a save switch produces a clean shareable link rather than one carrying a dangling id. useFilters is not cleared — categories and time ranges are save-independent and losing them on every switch would be annoying rather than safe.

7.4 Seeding, re-seeding, migrations & backup

"Version 1" — the first save — isn't blank. It's seeded from the existing sources:

  • Tags first. A canonical vocabulary of ~20–30 tags is written before any event exists, because tagging is part of the event seed step, not a later pass — and because timeline.membership_rules.byTag is unusable until the ids exist. Retro-tagging 80+ events by hand is the thing this ordering avoids.
  • Map state — every file in data/map_saves/ (not just lifestream_map_v1.json; see §7.5) → one grouping row per unified nation plus its grouping_country rows. The seed resolves each JSON code to a country.id per §3.1, minting an x: row where ISO has no numeric. The 74 synthesized "independent" groups are not imported — an independent nation is a country with no grouping_country row (§2.4).
  • Country renames — do not import countryNames wholesale. All 165 entries are default real-world names: map/src/components/Map.jsx:157 caches geo.properties.name on every click, so the map is a display cache, not authored content. Import only entries that differ from the topojson default; expect near-zero rows. Importing all 165 would fill country_override with rows that look authored and would then survive every fork.
  • Timeline events — parsed from data/story_docs/LIFEstream Bible.txt, World Timeline section from L886. It holds 80 bullets, not the ~50 previously claimed: Pre-Big One 12 · North Korean War 8 · Black Fever Era 21 · Reconstruction Era 39. Several are compound and split into more than one event, so 80 is a floor, not a target. Each bullet's stated precision drives when_precision and the derived when_min/when_max; rollDate() fills when (§2.3). Bullets that describe a span rather than a moment become a timeline or a project, not an event (§2.3).
  • Era timelines — the four section headers become timeline rows with kind='era' and explicit era_start/era_end. Where an era boundary is authored rather than canon (§3.4), the row's description says so.
  • Registry — characters, locations, and the project rows (NSPD-51A, Xero, Athena, Aurum, Afterlife) extracted from the Bible. Location rename chains are wired through superseded_by_location_id (§2.2).

Re-seeding is idempotent, and never destructive

scripts/seed.ts reads the source files, opens data/lifestream.db, and writes under the target save. It does not drop and recreate that save. Dropping it would delete rows that any fork's parent_save_id points at, orphaning every child save — and, once in-app editing exists, would silently destroy hand-authored edits made on top of the seed.

  • npm run db:seed is idempotent: it upserts by natural key (a Bible bullet's stable slug, a grouping's name, a country code) so re-running it updates what the sources changed and leaves everything else — including hand edits to rows the sources don't own — alone.
  • If the target save has children (any save with parent_save_id = it), a destructive re-seed is refused. The way to get a clean slate is db:seed --new-save, which creates a fresh save and leaves the existing tree intact.
  • npm run db:reset (drop the whole DB) refuses unless a dump under data/save_dumps/ is newer than the last write to lifestream.db.

Migration policy

Once the seed has run, the schema can no longer change by editing schema.ts and re-seeding — that is the destructive path just ruled out. So: every post-seed schema change ships a drizzle migration plus a backfill script, in the same commit. The migration moves the structure; the backfill moves the data (a new NOT NULL column gets its values computed for existing rows, a split column gets its parse, a renamed enum member gets its rewrite). A migration with no backfill is only acceptable when the change is provably data-free, and the commit says so.

Backup, before editing — not after

data/lifestream.db is gitignored. The moment in-app editing exists, that file is the only home for authored content — the Bible and the map JSON stop being the source of truth for everything typed into the side panel. So npm run db:dump (writing data/save_dumps/<save>.json via GET /api/saves/:id/dump) must exist and be part of the routine before the editing surfaces ship, not several phases later. The dumps are committed; the DB is not. This is also what makes db:reset safe and what gives POST /api/saves/import something to read.

7.5 Migrating off map/

map/ is the existing standalone React app this design replaces. It is not scaffolding to be deleted when the new Map view looks right — it currently holds authored content that exists nowhere else, and neither this document nor the implementation plan had ever named the migration. Three ordered steps, and the third is gated on the second.

  1. Port — the two pieces of real logic in map/ move to shared/src/geo/deriveFeatures.ts (§3.1): the France → French-Guiana split (map/src/components/Map.jsx:27-45) and the raw-feature-id fallback (:67-68). Everything else in map/ is UI the new Map view replaces.
  2. Drain — run map/ one final time and export every project in the picker, not just the one already sitting in data/map_saves/. This is the step that is easy to skip and impossible to undo: map/src/App.jsx:9,41 keeps a list of projects in localStorage['lifestreams_projects'] and only writes a file on demand, so any project the author made and never explicitly exported lives only in one browser's local storage and disappears with the app. Every exported file lands in data/map_saves/, and the seed imports all of them (§7.4) — one save per file.
  3. Delete — map/ is removed in its own commit, gated on the drain being complete and on parity being verified: for each imported world, the same countries belong to the same nations with the same names and colors as the old app rendered. Only then does the directory go. Keeping the deletion in a separate commit means it is one git revert away if parity turns out to be wrong.

8. Export pipeline (HTML first, more later)

We want exports across all four views into multiple formats eventually — but in v1 we ship HTML only and defer the rest until they're actually needed. The IR contract stays in place so adding formats later is cheap.

8.1 Why HTML first

  • Renders mermaid diagrams natively — every diagram (map, tech tree, family tree, corridor snapshot) goes through the same CDN script this doc uses. No rasterization, no Playwright, no Chromium download.
  • Browser does PDF for free — open the artifact, Cmd-P → "Save as PDF". Until we have a reason to automate this, the user's own browser is the renderer.
  • Easy downstream — HTML → Google Docs is literally copy-paste in the browser (formatting, tables, images preserved). HTML → Markdown is one library call (turndown). HTML → PDF via pandoc for batch jobs.
  • Zero new server deps — the renderer is a pure string-builder; no native libraries, no headless browser.

8.2 IR (defined upfront)

Even though only one renderer ships in v1, we define the IR now so future renderers slot in without per-view rework — N×M shrinks to N+M. Each view builds the same Document tree of blocks; any renderer walks that tree.

// --- inline formatting -------------------------------------------------
// The IR previously had none, while the builder specs already promised
// "actors and location as inline chips". A bare `text: string` cannot carry
// a chip, a link, or a code span, so every builder would have had to smuggle
// markup through as raw HTML — which is exactly what the IR exists to prevent.

type Inline =
  | string
  | Array<
        string
      | { b: Inline }
      | { i: Inline }
      | { code: string }
      | { link: { href: string, text: string } }   // href may be an internal #id
    >

type Cell = Inline | Block[]         // a table cell is inline text, or nested blocks

// --- blocks ------------------------------------------------------------
type Block =
  | { type: 'heading',   level: 1|2|3, text: string, id?: string }
  | { type: 'paragraph', content: Inline }
  | { type: 'list',      ordered: boolean, items: Block[][] }
  | { type: 'table',     rows: Cell[][], header?: Cell[] }
  | { type: 'callout',   tone: 'info'|'warn', body: Block[] }
  | { type: 'image',     mermaid?: string, svg?: string, src?: string,
                         alt?: string, caption?: string }
  | { type: 'anchor',    id: string }                    // for cross-refs
  | { type: 'link',      href: string, label: string }   // can be internal #id
  | { type: 'pageBreak' }

type Document = {
  title: string
  meta:  { saveId, runId?, exportedAt, scope, scopeParams?, viewSource }
  blocks: Block[]
}

The image block gains src and caption. It already carried generated vector content — a mermaid source string the HTML target renders client-side, or raw svg for diagrams a view produces directly (the World Map's d3-geo output). It now also carries a file reference, which is what character.portrait_path needs and which had nowhere to go in the old IR at all. Exactly one of mermaid / svg / src is set per block. alt is optional — a purely decorative diagram should not block an export on alt text — and renderers emit it whenever it is present. Later renderers that can't run mermaid in-place pre-render it to SVG via the mermaid CLI; an src image is copied or embedded as a data URI depending on the target.

8.3 Builders (one per view, v1)

Builders always emit the richest block. Renderers degrade. A builder must never branch on what the export target can do — the moment one does ("when the target supports SVG, also emit…"), the exact N×M dimension the IR exists to remove is back, because every builder now has to know about every format. The builder's job is "describe this view as completely as the IR allows"; the renderer's job is "express as much of that as I can, and fall back gracefully for the rest" — a Markdown renderer turning a mermaid image into a fenced mermaid block, a plain-text target dropping it and keeping the caption.
  • Timeline builder — Groups events by era/thread per the active timeline focus (§5.2). Emits heading per era, then a paragraph or list per event with date + title + description; actors and location as inline chips — now expressible, as Inline arrays with link parts pointing at internal anchors. Dates are rendered by precision (§2.3), never as the raw roll.
  • Map builder — One heading + table per save: rows are unified nations with member countries (from grouping_country), color, and (if computed) megacorp horizontal. Plus one image block with the rendered map SVG.
  • Tech Tree builder — One image block with a mermaid flowchart of the tree, then a list of tech events sorted by date; each item shows the node and its outgoing precedes edges as "→ X" lines. Project spans appear as their own list entries with their milestones nested.
  • Family Trees builder — Per family cluster: heading + indented list mirroring the tree, including the union structure ("Lazaro + Ines → Adan, X"). Character portraits emit as image blocks. Singletons → final section as list. No diagram in v1 — see below.

Each builder accepts a { diagrams, text } option pair so users can choose diagram-only, text-only, or both. That is a user choice about content, not a builder branching on target capability.

The diagram problem: two of the four views can only draw themselves in a browser.
  • Family Trees renders HTML <div>s. react-flow nodes are React components styled with CSS — there is no SVG document to dump to a string, and the previous plan's "the live react-flow SVG dump" does not exist. The only ways to get a picture are to run the app in a headless browser (ruled out — it is the single dependency §8.1 was designed to avoid) or to have the client capture it.
  • The Corridor is a WebGL scene. Same conclusion, more so.
  • The Map is the exception — d3-geo is pure geometry and runs perfectly well on the server.
v1 answer. The family export ships list-only: the indented list is the deliverable, and it is the form flat-text targets needed anyway. The map export renders server-side with d3-geo, reading the same shared/src/geo/deriveFeatures.ts feature set as the client — this duplicates the client's projection and color logic, and that duplication is accepted deliberately and stated here so the next person does not discover it as a bug. Keeping the geometry in shared/src/ is what keeps the two copies honest.

The future path is a client capture, not a headless browser. POST /api/export/asset accepts a client-rendered capture (a PNG or SVG the browser produced from the live view) and stores it; the builder then emits an image block pointing at it. The browser doing the rendering is the user's, already open, already showing the view.

8.4 HTML renderer (v1)

Walks the block tree and emits standalone dark-mode HTML matching the planning-doc aesthetic. image blocks with a mermaid source become <div class="mermaid">…</div> plus the same CDN script tag this doc uses; ones with svg are inlined; ones with src become <img> with the file embedded as a data URI so the artifact is a single portable file. Inline content maps to <b> / <i> / <code> / <a>. Pure function: (doc: Document) → string. The shell offers either "download as .html" or "preview in a side panel."

8.5 Scope

What's inside an export is independent of view + format. The same picker drives all four:

  • All — whole active save, every view (the canonical "world bible" export).
  • View — just the active view's content (most common single-view case).
  • Selection — whatever's currently selected: only Lazaro's life events, only the Castañeda family cluster, only the United Earth America grouping.
  • Filter — respects the current filters.categories / filters.tags / timeRange.
selection and filter are client-only state, so the request has to carry them. Neither primary nor the filter chips nor the Corridor's focus root exist anywhere on the server — they live in zustand and in the URL. A request that names scope: 'selection' and stops there is asking the server to reconstruct something it has never seen. So the export payload carries scopeParams (§8.7), and:
  • A saved manifest may only store the scopes that are reconstructible — all and view — or a resolved snapshot: the scopeParams frozen at the moment the manifest was saved. A manifest that stored a bare scope: 'selection' would silently mean something different every time it ran.
  • An optional runId pins which simulation run's grouping_metrics / nation_horizontal the map export reads. Without it, re-running last month's "World Bible" export after a new sim run produces a different document with no record of why.

8.6 Manifests (multi-view exports)

A manifest names a sequence of (view, scope) pairs. Manifests are stored in the manifest table (§2.1) so the canonical "World Bible" or "Lazaro one-pager" can be re-run after any edit without re-picking options — and, being per-save authored rows, they are copied on fork like anything else the author wrote.

{
  "title":  "LIFEstream — World Bible v1",
  "items": [
    { "view": "timeline", "scope": "all" },
    { "view": "map",      "scope": "all" },
    { "view": "tech",     "scope": "all" },
    { "view": "family",   "scope": "all" },

    // a non-reconstructible scope is storable ONLY as a resolved snapshot:
    { "view": "timeline", "scope": "selection",
      "scopeParams": { "primary": "character:char_lazaro", "rootTimelineId": "tl_world" } }
  ]
}

8.8 Deferred formats

When (and only when) a real need shows up:

  • Markdown — either a new renderer that walks the IR, or simply run the HTML artifact through turndown server-side. Inline maps cleanly onto Markdown emphasis and links; image blocks degrade to fenced mermaid blocks or sidecar SVG files. Cheapest add — pure JS, no native deps.
  • PDF — easiest path is pandoc html → pdf via shell-out, or weasyprint. Both heavier than the v1 stack but still way smaller than Playwright. Headless Chromium stays off the table unless we need exact browser-fidelity printing.
  • Google Docs — until we automate, copy-paste from the HTML artifact in Google Docs preserves formatting, tables, and images. When we want machine-driven export, add a Docs renderer that walks the IR and emits a batchUpdate via googleapis; mermaid blocks get pre-rendered to PNG via the mermaid CLI at that point.
