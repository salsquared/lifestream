Visualizer architecture

One shell, many lenses over one database. The world map, the time corridor, the tech tree, and the family trees are all views over the same LIFEstream tables. Selecting something in any view propagates to all the others.

1. The core idea

One Vite + React app that mounts a different visualizer depending on which tab you're on. All four visualizers fetch from the same Hono backend, which fronts the same SQLite database. A small set of zustand slice-stores (selection · filters · save · registry) holds shared state — nobody talks directly to anyone else.

Clicking Lazaro in the Family Trees filters the Time Corridor to his life events, highlights his birthplace on the Map, and dims unrelated tech nodes — without anyone having to wire the views to each other directly. They all just react to the same store.

2. The data layer (what lives in the DB)

Single SQLite file, accessed through Drizzle. Tables fall into three groups: core (used by every viz), map (used by the Map view + the data pipelines, §3), and timeline (used by Corridor + Tech Tree + Family Trees).

2.1 Core

  • save — a versioned project/snapshot. Every per-save row carries a save_id.
  • tag — global (no save_id). One canonical tag list shared across every save; rename once and every save sees the new name. Keeps timeline membership rules (tag = tech) stable across forks.
  • event_tag — joins tags to events. Since events are per-save, assignments still scope correctly even though tag definitions don't.

2.2 Registry (referenced by both timeline & map)

  • character — Lazaro, X, Ines, Bruce Deng, …
  • location — Disaster Ridge, Camp Oasis, Kauai lab, ET1, … When geo-locatable, map_ref_kind + map_ref_value point at a country (ISO-numeric) or a grouping id.
  • project — NSPD-51A, Xero, Athena, Aurum, Afterlife.
  • character_relation — explicit relationships between characters. v1 scope is family-only (parent-of / sibling-of / spouse-of / clone-of) since that's what the Family Trees view renders. Like relation, each edge is stored once: directional types (parent-of, clone-of) read from→to literally; symmetric types (spouse-of, sibling-of) are stored with a canonical ordering (lower id as from) and the renderer treats them as undirected — no mirror row, no drift. Other types (war-buddy, mentor, antagonist) can be added later without a schema change.

2.3 Timeline tables

  • event — the world timeline atom. Carries when (datetime, one shared TZ), range_before_event_id? / range_after_event_id? (for fuzzy Bible dates like "Late 2071" — point at the events that bracket this one; bounds are derived from their when values so the range auto-tracks when neighbors shift; rollDate() fills when), category (closed enum — see §2.5), tech_lane (only meaningful when category='tech'), location_id, project_id.
  • timeline, timeline_parent (DAG), timeline_member (manual roster) — the era/thread model. A timeline can also include events via membership_rules (jsonb predicate: by tag / by category / by time range / by location). See §2.6 for how a timeline view is composed at read time.
  • relation — event ↔ event graph. Three types: precedes, partOf, renames. Powers the Tech Tree edges directly. Stored once with a canonical direction (precedes from=A to=B means "A precedes B" / "B succeeds A"). Reverse views ("what succeeds X?") are derived at query time against the same row — no mirror records, no consistency hazard.
  • event_actor — many-to-many event ↔ character, with a role text field ("crew", "designer", "victim", "leader", …). Drives cross-view glow ("which characters appear in this event") and powers character-filtered views — but Family Trees doesn't render co-occurrence edges.

2.4 Map tables

  • country — global, not per-save. Real-world. Keyed by ISO 3166-1 numeric (§3.1); carries alpha-3 (display/debug) + default name.
  • country_override — per-save rename of a country (e.g. 840 → "United Earth America").
  • grouping — per-save unified nation. Carries name, color, and country_ids (jsonb array of ISO-numeric codes). Hand-drawn in the Map editor; the combine step (§3.3) computes its metrics — it doesn't pick the members.
  • grouping_metrics — output of the combine step (§3.3): per-save combined population / GDP / sector mix for each grouping, summed from its member countries' projected values.
  • nation_horizontal — output of the Megacorp classifier (§3.4): per-save industry horizontal + score per grouping. The World Map reads it as a color overlay.
  • bf_spread — output of the Black Fever spread simulation (§3.2): infection state per country per timestep. Driven partly by the per-country projections (development shapes spread/response). Shape + save-scope TBD until the sim is designed.
  • sim_run — the harness's run ledger (§3.5): one row per simulation run (stage, params, upstream run ids, status, timing). Every sim output above carries its run_id, so runs are individually versioned and comparable.

2.6 Algorithms & utilities

  • resolveTimeline(timelineId, saveId) — Compose the membership event set for a timeline (no live filters — see the split below).
    1. Walk timeline_parent transitively to gather this timeline + all descendants. A visited-set guards against cycles; cycles are also rejected at write time.
    2. For each timeline in that set: union timeline_member (manual roster) with events matching timeline.membership_rules (jsonb). Multiple predicate kinds AND together (byTag AND byCategory AND byTimeRange AND byLocation); within a kind, multiple values OR (any matching tag is a hit).
    3. Return the deduplicated event set sorted by when.
    Memoized per (timelineId, saveId) only — a stable key, so the cache actually hits. Invalidation is coarse: any per-save write drops every cached entry for that save. Re-runs are sub-millisecond at our expected scale (~50–500 events per save). Lives in server/src/services/resolveTimeline.ts.
  • Filtering is a separate pass, deliberately not in the memo key. The caller's live useFilters state (category chips, tag filter, time range, search) changes on every keystroke/scrub, so baking it into resolveTimeline's key would thrash the cache to near-zero hit rate. Instead, applyFilters(events, filters) runs as a cheap O(n) mask over the memoized membership set — client-side, since the membership set is already in hand. Membership is computed rarely and cached; filtering is recomputed freely and never cached.
  • rollDate(start: Date, end: Date) → Date — Uniform random datetime in [start, end] (one shared TZ). The event editor reads the when values of the events pointed at by range_before_event_id / range_after_event_id and passes those as start / end. If a side is unset (event has no neighbor on that side), the editor clamps with a sensible default — a wide world-timeline floor / ceiling. Re-rolling is just calling it again. Lives in shared/rollDate.ts so the UI editor and the seed script share the same logic.
  • Reverse relations. relation stores each edge once with a canonical direction (precedes from=A → to=B means "A precedes B" / "B succeeds A"). Reverse queries — "what succeeds X?", "what is X part of?", "what was X formerly called?" — run as SELECTs against the same row. No mirror records, no consistency hazard.
  • Glow derivation. When useSelection.primary changes, useSelection recomputes glow by following foreign keys from the primary entity (per §2.5) — e.g. primary event → its event_actor characters, location_id, project_id, event_tag tags. The per-primary recipe is the §6 table. This is purely client-side, which requires the join ids to already be on the client: each event payload embeds its own actorIds[] / tagIds[] / locationId / projectId (the registry cache only holds character/location/project rows, not the join tables, so glow can't be derived from the registry alone). At ~50–500 events per save the fully-hydrated event list is small enough to hold in memory — no dedicated glow endpoint needed.
  • Fork a save (the worker behind POST /api/saves/:id/fork) — In a single transaction: (1) insert a new save row with parent_save_id = :id; (2) for each per-save table (§7.1), copy rows under the new save_id with freshly generated row ids, building an old→new id map per table; (3) a second pass rewrites only per-save→per-save FKs in the copied rows using those maps (events ↔ location/project/character, event ↔ event self-refs in relation and range_*_event_id, timeline parents/members, event_tag.event_id, event_actor, etc.); (4) drop any memo cache keyed on the parent save. FKs into global tables are copied verbatim, never remapped — event_tag.tag_id still points at the shared tag, and grouping country_ids still point at the shared country. Returns the new save id.

3. Data pipelines (calculators & simulators)

Backend services that share one shape: read data → compute → write a table → feed a view. CLI + API, never the browser. They live here, right after the data layer, because the visualizations consume their output — we want the data pipelines running before we build the views on top of them.

The economic + epidemic work is one ordered chain:

  1. Project per country — project each individual country's metrics from now to the target year (§3.1).
  2. Run the BF sim — Black Fever spreads across the individual countries, using their projected metrics (§3.2).
  3. Combine into nations — sum the projected per-country values into each unified nation, using the manual editor's groupings (§3.3).
  4. Assign megacorps — give each combined nation an industry horizontal from its combined projected profile (§3.4).
Project per country, then combine. A nation's metrics are the sum of its member countries projected individually from now to the target year — we project each country as it stands today, then combine the projections. We never merge countries first and project the blob's development as a unit. Megacorps belong to the combined nation, but that nation's numbers come from the projected individuals.

The stages are modular. Each one is independently runnable — run a stage alone, run a prefix of the chain, or re-run a single stage in place. They hand off only through their persisted per-save tables (the per-country projection cache, bf_spread, grouping_metrics, nation_horizontal), never through in-memory chaining. So a downstream stage can run against an upstream stage's previously-saved output without recomputing it (run §3.1 once, then iterate on §3.2 alone; or tweak a grouping and re-run only §3.3 → §3.4). Each output is computed_at-stamped, so a stage can flag when its inputs are newer than its last run (stale) instead of forcing a full-chain rerun. The harness (§3.5) orchestrates this and versions each run.

3.1 Shared country data & per-country projection

Everything downstream needs real-world per-country numbers projected forward, so this is the shared foundation: identify each country, fetch + cache its real-world series, and project it individually from now to the target year. Because it operates on real-world countries — not on your fictional groupings — the projection is save-independent: computed once, reused by every save. Both the BF sim and the combine step read these per-country projections.

Country identity. The base layer is real-world countries (the topojson borders we render + the real stats we pull); all the fiction lives above it — unified nations are groupings (synthetic ids), renames are country_overrides. So the base country ID is just a join key the UI never shows. We key on ISO 3166-1 numeric (e.g. 840 for the territory currently called the USA):

  • Direct topojson join — the world-atlas borders we render key their features by ISO numeric, so the map needs no code lookup.
  • Direct population join — UN WPP publishes by the same numeric (M49) codes; population is the metric we most need, and it lines up for free.
  • Stable & unambiguous — numeric doesn't change when a country is renamed, and it sidesteps "whose alpha-3?" (ISO vs World Bank vs IOC variants disagree: DEU/GER, CHE/SUI, …).

Alpha-3 is kept only as a human-readable display/debug column on country — not a key. A small static lookup maps ISO-numeric → the codes the economic sources need where they differ (World Bank, IMF). This reverses the recent alpha-3 migration; see the decisions log (§3.7).

Data sources. Per-country series, fetched and cached locally (keyed by ISO-numeric) so a run is offline and repeatable.

Projection. Project each country individually from now to 2040 — the pre-collapse economic baseline the UEA uses to decide who merges with whom (Bible canon: UEA forms spring 2042 / first meeting May 1 2042; H-Mega megacorps formed by Jan 1 2043; country mergers complete by Jan 1 2047). 2040 is the fixed horizon; the projection method is still open (§3.6).

3.2 Black Fever spread simulation

Runs over the individual countries, before they're combined, using their projected metrics — a country's development level (population at least, likely GDP / GDP-per-capita) drives how fast BF spreads, how it's contained, and the quality of care. Simulate BF moving across the world over time — origin, transmission, containment — calibrated against the Bible's BF-era events. The one pipeline that needs both a new output table and a new visualization.

  • Input — the per-country projections from §3.1 (population at least) as per-country development variables; plus an origin + transmission parameters + an adjacency / travel graph + a time range.
  • Output — bf_spread, a per-save table (shape TBD): infection state per country per timestep.
  • Visualization — a time-scrubbing map: drag a time slider, watch the map repaint as BF spreads. Shares mechanics with the parked "UEA Membership Map over Time" (§9) — likely a Map overlay with a time control, or its own animated view.
  • Open — spatial granularity; model family (SIR / SEIR vs agent-based); how tightly to fit canon vs let it run free; overlay-on-Map vs dedicated view.

3.3 Combine into nations (nation-grouping calculator)

Fed by the manual map editor (which countries form each unified nation) and the per-country projections (§3.1). For each grouping, it sums the projected member-country metrics over country_ids into the nation's combined figures at the horizon. It does not pick members (you do, in the editor) and does not project a combined blob — it combines already-projected individuals.

  • Input — the active save's grouping rows (your country_ids) + the per-country projections (§3.1).
  • Compute — sum the projected population and GDP over country_ids; derive combined GDP-per-capita; build a combined sector mix (GDP-weighted value-added, or a merged export basket / aggregated RCA).
  • Output — grouping_metrics (save_id, grouping_id, pop, gdp_real, gdp_per_capita, sector_mix, computed_at), per save. Recompute when a grouping's membership changes in the editor.
  • Visualization — no new view: the Map sidebar reads it for a selected nation, and Megacorp (§3.4) reads it as input.

3.4 Megacorp — industry horizontals

The last economic step, and the payoff. Canon (Bible §"Tiered Corporate Structure"): business horizontals were divided among a designated number of megacorporations by each host nation's pre-collapse economic standing. So this stage reads each post-merger nation's combined 2040 profile (the pre-collapse baseline, §3.1) and hands it the horizontal(s) it dominates. These are the H-Megas (Horizontal Megacorporations), formed by Jan 1, 2043. Output is nation_horizontal, which the World Map (§5.1) renders as a color overlay.

The taxonomy is emergent, not a fixed list. We don't hand-pick the set of horizontals. The classifier clusters the combined 2040 economic profiles across the post-merger nations; the number of horizontals falls out of the data and the nation count (each nation anchors the stratum it dominates). The categories are discovered, and they scale with how the world merged.

Horizontal vs vertical (both canon). A horizontal is one stratum of the supply chain owned by one H-Mega — this stage's output. A vertical is the canon progression that stacks H-Megas upward: H-Mega → S-Mega (Syndicated) → Monolithic. S-Megas combine multiple H-Megas; they're in scope but designed later (§3.6). This stage produces the H-Mega horizontals the syndicates are built from.
  1. Cluster the post-merger nations' combined 2040 profiles (sector mix, GDP, GDP-per-capita) → an emergent set of horizontals.
  2. Assign each nation the horizontal(s) it dominates by pre-collapse standing; a designated count of H-Megas falls out.
  3. Write nation_horizontal (save_id, run_id, grouping_id, horizontal, score, computed_at).

Packaging: the whole chain lives under server/src/services/simulation/ — one module per stage (project · bfSim · combine · classify), named for what it is (a stack of world simulations, not just its last step). Each stage is independently invokable: CLI scripts/simulate.ts <stage|all> and API POST /api/simulation/<stage> run a single stage or the full sequence, with the per-save tables as the hand-off between them. Backs a per-stage "recompute" control in the Map sidebar.

3.5 Run manager (the harness)

The stages (§3.1–§3.4) are modular, but something has to orchestrate them and version their runs — that's the harness. It's a thin layer over the stages, not a fifth stage; the CLI and /api/simulation go through it.

Two version axes — don't conflate them:

  • Save (§7) — a branch of the authored world: groupings, events, characters. Forking copies authored data.
  • Run — a parameterized execution of a sim stage: a projection method, a BF origin + seed, a target year. A save can hold many runs; you compare them.

What the harness does:

  • Records every run in sim_run — stage, params, the upstream run ids it consumed, status, timing (and save_id when the stage is save-scoped). This is the provenance/lineage record: re-running the same params against the same inputs reproduces the output (BF's stochastic stage takes a seed in its params, so even it is reproducible).
  • Versions the data — every output row carries a run_id, so multiple parameterizations coexist (BF origin A vs B) and prior runs are retained for comparison until pruned. A per-(scope, stage) pointer marks the active run that views read by default; pin a different run to compare.
  • Orchestrates the DAG — given a requested stage (or "all"), it resolves dependency order, reuses fresh upstream runs, reruns stale ones (an input's computed_at newer than the dependent run's), and refuses to run a stage whose upstream output is missing.

Run scope follows stage scope: the per-country projection (§3.1) is save-independent, so its runs are global; the combine (§3.3) and classify (§3.4) are per-save; BF's scope (global over real countries, or per-save) is an open question (§3.6).

3.6 Open questions (projection, combine & megacorp)

  1. GDP projection method. Log-linear on per-capita real GDP × projected pop? ARIMA? Solow-style? Convergence model? Decide after eyeballing the historical series.
  2. Sector source. WDI value-added (coarse, simple) vs OEC/Comtrade RCA (sharp, more ingest work).
  3. Emergent clustering. How to cluster the 2040 profiles into horizontals — which features, which algorithm, and how the "designated number" of H-Megas is derived from the nation count.
  4. Syndicate (S-Mega) formation. Now that syndicates are in scope: what rule stacks H-Megas into S-Megas (and S-Megas into Monolithics)? A later stage in the chain + its own output table + the §9 syndicate map.
  5. Scope. Compute metrics + horizontals for single-country groupings too, or only multi-country unified nations?
  6. Currency / base year for GDP comparisons (constant 2015 vs 2020 USD).
  7. Failure modes. Sparse-history small states; codes some datasets don't cover (Palestine, Western Sahara, Somaliland, Taiwan in IMF).
  8. BF run scope. Is the BF sim save-independent (spreads over real countries + global projections) or per-save (calibrated to that save's BF-era canon)? Decides whether bf_spread carries a save_id.
  9. Run retention. How many runs per (scope, stage) to keep before pruning, and what the default "active run" pointer follows (latest, or pinned).

4.2 Shared state (zustand slice-stores)

Four small slice-stores. Splitting by concern keeps subscriptions narrow — a Tech Tree node doesn't re-render when the save name changes. Every view reads from these and writes to these; nobody talks directly to any other view.

  invalidate(): void
}

The primary + glow split resolves "click event, glow its actors" cleanly: setPrimary({type:'event', id}) sets what was clicked, and the store internally derives glow from event_actor, location_id, project_id, event_tag. Views read primary to know what was clicked and glow to know what to highlight around it.

4.3 View switcher & URL state

Top-bar tabs are enough for v1. Each tab is a route under /v/<view>. Active view is preserved in the URL.

Selection, active save, and filters all serialize to URL search params — e.g. /v/timeline?primary=event:evt_athena_launch&save=sav_canon&cat=tech,disaster&from=2034&to=2050. For a link to be truly shareable, the filter state has to ride along too — otherwise the recipient sees an unfiltered view at the right selection. So useSelection, useSave, and useFilters sync to the URL via a single effect at the shell level. Only primary is serialized from selection (glow is derived on load, not stored). Browser back/forward navigates the whole state; reload restores it exactly.

Cmd-K opens a command palette that can switch views and jump to entities ("go to Lazaro" → ?primary=character:char_lazaro, "show Project Xero" → ?primary=project:proj_xero). The palette is just another URL writer.

5. The four planned visualizers

5.1 World Map (2D)

Select countries, group them into unified 2046 nations, version those groupings, persist to the DB. Plain d3-geo + topojson-client, no wrapper library — every d3 projection (Mercator / Equal-Earth / Natural Earth II / Robinson / orthographic / Winkel Tripel / …) is swappable in one line.

Readscountry, country_override, grouping; optionally grouping_metrics (sidebar stats) and nation_horizontal (color overlay)
Rendersd3-geo for projection math, topojson-client for parsing borders, plain country <path> elements emitted by React. Projection picker in the sidebar lets you flip between flat projections at runtime.
EditsClick country → toggle into the current editing grouping. Create / rename / color groupings. Per-save country renames via right-click.
Cross-links outClick country → setPrimary({type:'country', id}). Click grouping label → setPrimary({type:'grouping', id}).
Cross-links inGlow any country/grouping whose id is in glow.countryIds / glow.groupingIds (e.g. set when a located event or a character is the primary).

5.2 Time Corridor (3D)

The depth-stratified scrolling corridor — see implementation.html for the build sequence.

5.3 Tech Tree (3D node-graph)

A directed graph of technological enablement. Reads exactly the same event and relation tables as the Corridor — but only events with category: tech, and only precedes / partOf relations between them. Different lens, same data.

Readsevent WHERE category='tech', relation WHERE type IN (precedes, partOf)
LayoutX = date (shared time scale with Corridor). Y = swimlane by event.tech_lane (energy / propulsion / computing / neural / biomedical / megastructure). Lane is a simple enum field on the event — no graph-layout library needed at the scale we have.
RendersR3F + drei — exactly the same stack as the Corridor. Reuses the EventNode component so the two views share aesthetics and selection visuals. drei <Line> for edges.

5.4 Family Trees (2D)

Plain family trees, one per cluster of related characters. Most of the cast won't have any family data (we don't track Bruce Deng's lineage) — those render as singleton cards in a row below the trees. The actual family content is small: the Castaneda family is the main tree (Lazaro + Ines → Adan, X), Atticus + Deimos is a two-node clone-of "tree", and that's about it for v1. No force simulation, no co-occurrence edges, no "web" — just the family relationships we actually care about.

6. Cross-view linking

Every cross-link is "the source view calls useSelection.setPrimary(...); useSelection derives the glow set by following FKs; target views read primary + glow and react." No view talks to any other view directly. Adding a fifth view doesn't change any existing view's code.

The shape of the auto-derivation: when primary is an event, glow includes that event's actors / location / project / tags. When primary is a character, glow includes every event they appear in plus those events' locations and projects. When primary is a country, glow includes every event located there. And so on — driven by the foreign keys already in §2.5.

7. Saves & versioning (DB-backed, app-wide)

Versioning is app-wide via a save table that every visualizer respects. Every editable row in every entity table carries a save_id foreign key. The shell holds an "active save" in state; every API call passes it; every SELECT filters on it. Forking a save (e.g. "branch this into Version 2") inserts a new save row and copies all per-save rows from the parent.

save {
  id          uuid
  name        text          // "Version 1", "What if Athena succeeded?", "Movie canon"
  description text
  created_at  timestamp
  parent_save_id  uuid?     // for forks
  is_archived bool
}

7.1 What's in a save

  • In-save (per-version): event, timeline, timeline_parent, timeline_member, relation, character, character_relation, location, project, grouping, country_override, event_tag, event_actor, grouping_metrics, nation_horizontal, bf_spread (pipeline outputs, §3).
  • Shared (global): country (real-world borders + default names), tag (canonical tag list).

7.2 Operations

  • POST /api/saves — create a blank or forked save
  • GET /api/saves — list
  • POST /api/saves/:id/fork — copy all per-save rows under a new save id
  • DELETE /api/saves/:id — soft delete (sets is_archived); hard delete via separate endpoint
  • POST /api/saves/:id/dump — emit a JSON dump of every row under this save, for backup / sharing (distinct from /api/export in §8, which renders documents)
  • POST /api/saves/import — load a JSON dump under a new save id

7.3 UX in the shell

Save picker lives in the top bar next to the view switcher. Shows current save name + a dropdown for switching / forking / renaming. Switching saves replays every view's data load — fast because everything is keyed on a single column.

7.4 Initial seeding

"Version 1" — the first save — isn't blank. It's seeded from the existing sources:

  • Map state — data/map_saves/lifestream_map_v1.json (29 unified nations + ~70 independents) → one grouping row per nation (with its country_ids array) under save_001. The seed maps the JSON's codes to ISO-numeric (the canonical key, §3.1) — undoing the recent alpha-3 migration as it loads.
  • Timeline events — parsed from data/story_docs/LIFEstream Bible.txt (the World Timeline section, ~50 dated entries between 2021 and 2084-04-25). Fuzzy dates run through rollDate(). Era timelines (Pre-Big One, NK War, Black Fever, Reconstruction) are created from the section headers.
  • Registry — characters, locations, and the project rows (NSPD-51A, Xero, Athena, Aurum, Afterlife) extracted from the Bible.

The seed is one-shot: scripts/seed.ts reads the source files, opens data/lifestream.db, and writes everything under a freshly created save. Re-running drops and recreates that save; it doesn't touch any other save you've forked off of it.

8. Export pipeline (HTML first, more later)

We want exports across all four views into multiple formats eventually — but in v1 we ship HTML only and defer the rest until they're actually needed. The IR contract stays in place so adding formats later is cheap.

8.1 Why HTML first

  • Renders mermaid diagrams natively — every diagram (map, tech tree, family tree, corridor snapshot) goes through the same CDN script this doc uses. No rasterization, no Playwright, no Chromium download.
  • Browser does PDF for free — open the artifact, Cmd-P → "Save as PDF". Until we have a reason to automate this, the user's own browser is the renderer.
  • Easy downstream — HTML → Google Docs is literally copy-paste in the browser (formatting, tables, images preserved). HTML → Markdown is one library call (turndown). HTML → PDF via pandoc for batch jobs.
  • Zero new server deps — the renderer is a pure string-builder; no native libraries, no headless browser.

8.2 IR (defined upfront)

Even though only one renderer ships in v1, we define the IR now so future renderers slot in without per-view rework — N×M shrinks to N+M. Each view builds the same Document tree of blocks; any renderer walks that tree.

type Block =
  | { type: 'heading',   level: 1|2|3, text: string, id?: string }
  | { type: 'paragraph', text: string }
  | { type: 'list',      ordered: boolean, items: Block[][] }
  | { type: 'table',     rows: string[][], header?: string[] }
  | { type: 'callout',   tone: 'info'|'warn', body: Block[] }
  | { type: 'image',     mermaid?: string, svg?: string, alt: string, caption?: string }
  | { type: 'anchor',    id: string }                    // for cross-refs
  | { type: 'link',      href: string, label: string }   // can be internal #id
  | { type: 'pageBreak' }

type Document = {
  title: string
  meta:  { saveId, exportedAt, scope, viewSource }
  blocks: Block[]
}

Images carry either a mermaid source string (rendered client-side by the HTML target) or raw svg (only used for diagrams that views produce directly — e.g. the World Map's d3-geo output). Later renderers that can't run mermaid in-place will pre-render to SVG via the mermaid CLI.

8.3 Builders (one per view, v1)

  • Timeline builder — Groups events by era/thread per the active timeline filter. Emits heading per era, then a paragraph or list per event with date + title + description; actors and location as inline chips.
  • Map builder — One heading + table per save: rows are unified nations with member countries, color, and (if computed) megacorp horizontal. Plus one image block with the rendered map SVG — the same SVG the view produces, dumped to string.
  • Tech Tree builder — One image block with a mermaid flowchart of the tree, then a list of tech events sorted by date; each item shows the node and its outgoing precedes edges as "→ X" lines.
  • Family Trees builder — Per family cluster: heading + indented list mirroring the tree (always — flat-text targets need the textual lineage). When the export target supports SVG, also an image block with the live react-flow SVG dump for that cluster. Mermaid doesn't render genealogy idiomatically (no spouse-bars, sibling links awkward) so the diagram path uses react-flow's own output rather than a mermaid flowchart. Singletons → final section as list.

Each builder accepts a { diagrams, text } option pair so users can choose diagram-only, text-only, or both.

8.4 HTML renderer (v1)

Walks the block tree and emits standalone dark-mode HTML matching the planning-doc aesthetic. Mermaid blocks become <div class="mermaid">…</div> plus the same CDN script tag this doc uses. Pure function: (doc: Document) → string. The shell offers either "download as .html" or "preview in a side panel."

8.5 Scope

What's inside an export is independent of view + format. The same picker drives all four:

  • All — whole active save, every view (the canonical "world bible" export).
  • View — just the active view's content (most common single-view case).
  • Selection — whatever's currently selected: only Lazaro's life events, only the Castaneda family cluster, only the United Earth America grouping.
  • Filter — respects the current filters.categories / filters.tags / timeRange.

8.6 Manifests (multi-view exports)

A manifest names a sequence of (view, scope) pairs. Manifests are saved in the DB so the canonical "World Bible" or "Lazaro one-pager" can be re-run after any edit without re-picking options.

{
  "title":  "LIFEstream — World Bible v1",
  "items": [
    { "view": "timeline", "scope": "all" },
    { "view": "map",      "scope": "all" },
    { "view": "tech",     "scope": "all" },
    { "view": "family",   "scope": "all" }
  ]
}

8.7 Backend (v1)

  • POST /api/export — body: { saveId, view | manifestId, scope }. Format is implicit (HTML) in v1 → returns the rendered HTML string or a saved-artifact URL.
  • GET / POST / PATCH / DELETE /api/export/manifests — CRUD on saved manifests.

8.8 Deferred formats

When (and only when) a real need shows up:

  • Markdown — either a new renderer that walks the IR, or simply run the HTML artifact through turndown server-side. Diagrams degrade to fenced mermaid blocks or sidecar SVG files. Cheapest add — pure JS, no native deps.
  • PDF — easiest path is pandoc html → pdf via shell-out, or weasyprint. Both heavier than the v1 stack but still way smaller than Playwright. Headless Chromium stays off the table unless we need exact browser-fidelity printing.
  • Google Docs — until we automate, copy-paste from the HTML artifact in Google Docs preserves formatting, tables, and images. When we want machine-driven export, add a Docs renderer that walks the IR and emits a batchUpdate via googleapis; mermaid blocks get pre-rendered to PNG via the mermaid CLI at that point.

8.9 Directory layout

server/src/services/export/
  builders/
    timeline.ts
    map.ts
    tech.ts
    family.ts
  renderers/
    html.ts                      # v1
  manifests.ts                   # CRUD on saved manifests
shared/types/export.ts            # Block & Document IR

Why this scales. A fifth view means one new builder. A second format means one new renderer. v1 ships exactly one of each on the renderer side, but the IR contract is in place so the second renderer doesn't require touching any view code.
