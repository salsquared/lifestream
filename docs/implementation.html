Visualizer — implementation plan

Phased build plan for the LIFEstream visualizer: one shell + four mounted views over one SQLite DB. Tasks indexed PX.Y.Z. Checkbox state saves to localStorage on this device. Companion to architecture.html.

Stack (decided)

Shell
Vite + React + TypeScript + React Router + zustand (shared selection / filters / active-save / registry cache).
3D views
Time Corridor + Tech Tree: three + @react-three/fiber + @react-three/drei + @react-three/postprocessing. d3-scale for time math, d3-zoom for trackpad input.
2D Map
d3-geo + topojson-client → plain SVG <path> elements. No wrapper library. Any d3 projection swappable at runtime (Mercator / Equal-Earth / Natural Earth II / Robinson / orthographic / Winkel Tripel …).
2D Family Trees
@xyflow/react (react-flow) for node-graph rendering + d3-hierarchy for initial tree layout.
Backend
Hono on Node (TypeScript). Serves /api/*.
Database
SQLite at data/lifestream.db, accessed via drizzle-orm + better-sqlite3. Migrations via drizzle-kit.
Tooling
npm workspaces (client/, server/, shared/), shared tsconfig.base.json, ESLint + Prettier at root.
Export
View state → a Document IR (block tree) → renderers. v1 ships an HTML renderer only (mermaid diagrams render via the CDN script; browser handles PDF via print). Markdown / PDF / Google Docs deferred. See architecture §7.

Resolved decisions

  1. Date precision. Every event has a when datetime (date + time of day, single timezone). For fuzzy source dates ("Late 2071"), the event points at bracketing events via range_before_event_id / range_after_event_id; their when values bound the roll. Roller is its own utility (P8).
  2. Rename chains. One Location per place. A rename is an event located there, chained to the prior name via a renames relation. No event.kind field — dropped as redundant with category + tags.
  3. Characters / Locations / Projects registry. First-class tables alongside events. Lifespan / project dates are plain date columns (not event refs).
  4. Era overlap. Events whose date falls in both an era and an adjacent era appear in both — by design.
  5. Relations. Three types — precedes / partOf / renames. Stored once with a canonical direction; reverse views ("what succeeds X?") derived at query time. Tag overlap on create surfaces relation suggestions; user confirms.
  6. One app, four views. Unified shell — no separate apps. Existing map/ rebuilt as a view; the standalone folder goes away.
  7. Family Trees renderer. react-flow — gets pan / zoom / drag / minimap / connect-to-edit for free.
  8. Saves model. Every editable row carries save_id. Active save lives in the shell. Forking copies all per-save rows (FKs into global tables — tag, country — copied verbatim, never remapped). Replaces map/'s localStorage "projects" concept across the whole app.
  9. character_relation scope. v1 family-only (parent-of / sibling-of / spouse-of / clone-of). Stored once; symmetric types (spouse / sibling) use canonical ordering. Other types add later without schema change.
  10. Map renderer. Plain d3-geo + SVG. react-simple-maps dropped. A 3D-globe view via react-globe.gl is parked as a future second map view (see architecture §9).
  11. Selection model. useSelection holds a single primary ({type, id}) plus a derived glow set; setPrimary recomputes glow by following FKs. No flat per-type id fields. (architecture §3.2)
  12. Tags global. tag has no save_id — one canonical list shared across saves so timeline membership rules stay stable across forks. event_tag assignments remain per-save.
  13. URL state. primary + active save + filters all serialize to URL search params at the shell level — shareable, reload-restorable. glow is derived on load.
  14. Closed enums. event.category ∈ {tech, political, military, disaster, scientific, cultural, personal, project}. event.tech_lane ∈ {energy, propulsion, computing, neural, biomedical, megastructure} (only when category=tech).
  15. Groupings. A grouping carries its members as a country_ids jsonb array (ISO-numeric) — no grouping_country join table.
  16. Country key. Canonical country id = ISO 3166-1 numeric (joins the topojson + UN WPP directly; alpha-3 kept only as a display column). Reverses the recent alpha-3 migration. (architecture §3.1)
  17. Simulation chain. The economic/epidemic pipelines live under server/src/services/simulation/ (route /api/simulation), not megacorp — the megacorp list is just the chain's last step. Order: project per-country → BF sim → combine → classify. Modular: each stage is independently runnable (simulate <stage|all> / POST /api/simulation/<stage>), handing off only through persisted tables. A harness orchestrates the DAG and versions each run (sim_run ledger + run_id on outputs) — runs are a second version axis on top of saves. Held until open questions are resolved. (architecture §3, esp. §3.5)

P1 Data layer — full schema, seed, read APIs

Goal: every table from architecture.html §2 exists. The Bible's World Timeline and the existing data/map_saves/lifestream_map_v1.json are both seeded. Reading any timeline through /api/timelines/:id/resolve returns the correct event list. Reading the map returns the same groupings the current map/ sees.

  • P1.1Schema: core + saves

    The save table is foundational — every per-save row references it. Implementing this first prevents a painful migration later.

    • P1.1.1save: id, name, description, created_at, parent_save_id?, is_archived
    • P1.1.2tag (global — no save_id: id, name, color, description?), event_tag join (per-save via event_id)
  • P1.2Schema: registry (character / location / project / character_relation)
    • P1.2.1character: id, save_id, name, lifespan_start?, lifespan_end?, role, bio?, portrait_path?
    • P1.2.2location: id, save_id, name, description?, lat?, lng?, map_ref_kind? ('country'|'grouping'), map_ref_value?
    • P1.2.3project: id, save_id, name, description, date_start?, date_end?, status (planned/active/succeeded/failed/cancelled), lead_character_id?
    • P1.2.4character_relation: id, save_id, from_character_id, to_character_id, type (family-only enum for v1). Stored once; symmetric types use canonical ordering (lower id as from)
  • P1.3Schema: timeline (events / timelines / relations)
    • P1.3.1event: id, save_id, title, description, when, range_before_event_id?, range_after_event_id?, category (closed enum), tech_lane? (only when category=tech), location_id?, project_id?
    • P1.3.2timeline: id, save_id, name, description?, membership_rules? (jsonb: {byTag?, byCategory?, byTimeRange?, byLocation?}). Display fields (color, default viewport) as UI extras.
    • P1.3.3Join tables: timeline_parent (DAG edges), timeline_member (manual roster), event_actor (event ↔ character, with role text field)
    • P1.3.4relation: id, save_id, from_event_id, to_event_id, type (precedes / partOf / renames), note. Canonical direction; reverse derived.
  • P1.4Schema: map (country / overrides / groupings / horizontals)
    • P1.4.1country: iso_numeric PK, alpha3 (display/debug), name. Global, not per-save.
    • P1.4.2country_override: save_id + iso_numeric PK, name (per-save rename)
    • P1.4.3grouping: id, save_id, name, color, country_ids (jsonb array of ISO-numeric) — no join table
    • P1.4.4nation_horizontal: save_id + grouping_id PK, horizontal, score, computed_at (populated later by the simulation chain — architecture §3)

P2 Saves UI & active-save plumbing

Goal: a save picker in the top bar lets you switch / fork / rename / archive saves. Every API call carries the active save_id; switching saves reloads the views without a hard refresh.

  • P2.1Save mutation endpoints
    • P2.1.1POST /api/saves — create blank
    • P2.1.2POST /api/saves/:id/fork — copy all per-save rows under a new save id
    • P2.1.3PATCH /api/saves/:id — rename / edit description
    • P2.1.4DELETE /api/saves/:id — soft delete (is_archived)
    • P2.1.5POST /api/saves/:id/dump & POST /api/saves/import — JSON dump and load (distinct from /api/export in P12, which renders documents)
  • P2.2Server-side fork procedure

    Single transaction. For each per-save table, INSERT INTO ... SELECT ... rewriting save_id and any per-save→per-save foreign keys (event ids, character ids, range_*_event_id, relation self-refs, etc.) via an id-remapping table built as we go. FKs into global tables are copied verbatim — event_tag.tag_id → tag, grouping country_ids → country — never remapped.

  • P2.3Active-save plumbing on the client
    • P2.3.1Active save id in stores/save.ts; persisted to localStorage
    • P2.3.2API client wrapper appends ?save=:id to every request
    • P2.3.3On save switch, invalidate all query caches; views re-fetch
  • P2.4Save picker UI

    Top-bar dropdown showing current save name. Actions: switch, fork (with name prompt), rename, archive, export, import.

P12 Export pipeline (HTML)

Goal: pick a view + scope and get a standalone dark-mode HTML doc — prose, tables, and mermaid diagrams rendered via the CDN script. Manifests bundle multiple views into one artifact. Markdown / PDF / Google Docs are deferred (architecture §7).

  • P12.1Document IR types (shared/types/export.ts)

    The contract between builders and renderers. Defined upfront so future formats slot in without per-view rework (N×M → N+M).

    • P12.1.1Block union: heading / paragraph / list / table / callout / image (mermaid? | svg?) / anchor / link / pageBreak
    • P12.1.2Document: title, meta {saveId, exportedAt, scope, viewSource}, blocks[]
  • P12.2Builders — one per view (server/src/services/export/builders/)

    Each turns a (view, scope) into a Document. Accept a { diagrams, text } option pair.

    • P12.2.1timeline.ts — heading per era, then list/paragraph per event (date, title, desc, actors + location as inline chips)
    • P12.2.2map.ts — table of groupings (members, color, horizontal if computed) + an image block with the d3-geo map SVG
    • P12.2.3tech.ts — mermaid flowchart image + list of tech events with their outgoing precedes edges
    • P12.2.4family.ts — per cluster: indented list (always) + react-flow SVG image when target supports it (mermaid doesn't do genealogy idiomatically); singletons as a final list
  • P12.3HTML renderer (renderers/html.ts) — v1, the only renderer

    Pure function (doc: Document) → string. Walks the block tree → standalone dark-mode HTML matching the planning-doc aesthetic. image.mermaid blocks become <div class="mermaid">…</div> + the same CDN script this plan uses; image.svg inlined directly. No server deps, no headless browser.

  • P12.4Scope resolution

    Resolve the four scopes into the row set a builder receives: all (whole save), view (active view's content), selection (current primary + its glow), filter (current useFilters).

  • P12.5Manifests (multi-view bundles)
    • P12.5.1manifest table: title + ordered (view, scope) items, per save
    • P12.5.2Concatenate each item's Document into one (e.g. the "World Bible") — re-runnable after edits
  • P12.6Backend + UI + CLI
    • P12.6.1POST /api/export { saveId, view | manifestId, scope } → HTML string / artifact URL
    • P12.6.2GET/POST/PATCH/DELETE /api/export/manifests — CRUD
    • P12.6.3Shell export dialog — view/scope picker; "download .html" or "preview in side panel"
    • P12.6.4scripts/export.ts — run a manifest from the terminal
  • P12.7(Deferred) Markdown / PDF / Google Docs

    Not in v1. When needed: Markdown via turndown over the HTML artifact (or an IR renderer); PDF via browser print or pandoc/weasyprint (no Playwright); Google Docs via copy-paste from HTML, or later an IR renderer emitting a googleapis batchUpdate. The IR + builders are already in place, so each is one new renderer.
