Visualizer — implementation plan

Phased build plan for the LIFEstream visualizer: one shell + four mounted views over one SQLite DB. Tasks are indexed PX.Y.Z and every id is a real anchor — click a task id to copy a deep link (e.g. P1.8). Checkbox state saves to localStorage on this device. Companion to architecture.html.

Stack (decided)

Shell
Vite + React + TypeScript + React Router + zustand — five slice-stores, not four: selection · filters · save · registry · world (architecture §4.2). world was added on 2026-09-01 and holds the events, timelines, relations, groupings and the groupingOf country→grouping index; both glow derivation and §6's grouping→countries→events hop need them, and the other four stores hold none of it.
3D views
Time Corridor + Tech Tree: three + @react-three/fiber + @react-three/drei + @react-three/postprocessing. d3-scale for time math, d3-zoom for trackpad input.
2D Map
d3-geo + topojson-client → plain SVG <path> elements. No wrapper library. Geometry from world-atlas@2 countries-50m.json, vendored into client/public/topojson/ at a pinned version (P0.6) — not CDN-fetched. Any d3 projection swappable at runtime (Mercator / Equal-Earth / Natural Earth II / Robinson / orthographic / Winkel Tripel …).
2D Family Trees
@xyflow/react (react-flow) for node-graph rendering + d3-hierarchy for initial tree layout over a synthetic union-node graph.
Backend
Hono on Node (TypeScript). Serves /api/*.
Database
SQLite at data/lifestream.db, accessed via drizzle-orm + better-sqlite3. Migrations via drizzle-kit.
Testing
vitest at the root; npm test runs it; specs live in tests/. Four targeted tests only (country import, resolveTimeline(), fork remap, rollDate) — not a coverage push. Database-backed specs use a fresh :memory: SQLite per file on the default forks pool (the test-fixture decision).
Tooling
npm workspaces (client/, server/, shared/), shared tsconfig.base.json, ESLint + Prettier at root. Cross-workspace imports go through @shared/* → ./shared/src/* and @server/* → ./server/src/*; every file the shared workspace publishes lives under shared/src/, never directly under shared/ (the toolchain facts).
Export
View state → a Document IR (block tree) → renderers. v1 ships an HTML renderer only (mermaid diagrams render via the CDN script; browser handles PDF via print). Markdown / PDF / Google Docs deferred. See architecture §8.

Build order (why the phases sit where they do)

The plan is sequenced so that every irreversible decision is validated by a rendered view before the expensive hand-authoring depends on it. Schema lands once, in migration #1. The map renders against 237 real authored country codes before a single event references the schema. A twelve-event thin slice opens the Corridor before the remaining sixty-eight are transcribed. The fork lands only once two views exist to show two saves diverging.

Review policy — which phases get what

Review is not free and not uniform. A phase is worth a reviewer in proportion to how expensive its defects are to unwind — not to how much code it contains.

The distinction that decides it: inherited vs terminal. An inherited phase produces something later phases build on — a schema, a seed that writes authored content, a contract other code copies. Its defects compound, and each later phase makes them more expensive. A terminal phase renders something. Its defects are visible on screen and cost the same to fix whenever you find them. Spend review on the first kind.

The evidence for this is in the 2026-09-04 hardening entry: reviewing the schema before migration #1 found a key that could not store canon, six missing precision columns, two incompatible datetime spellings and fourteen columns admitting cross-save corruption. The same review a week later would have found the same defects as table rebuilds against hand-authored data.

The final sweep

Before the project is called done, one full rank-0 suite — adversarial correctness, completeness against this plan, and security — across the whole codebase. This is the one place a parallel fan-out is justified rather than a single reviewer: it is a release gate, the axes are genuinely unrelated, and by then the terminal phases have accumulated without individual review, which is exactly the debt this sweep exists to settle.

Deferred, and owed. P1 and P2 shipped without a reviewer. Their headline properties were proven by execution instead — idempotent seeding, a rebuild reproducing identical content, 237/237 codes resolving, parity against the imported world, and a mutation pass confirming all four specs fail when their implementation is broken. That is not the same as a review, and both are on the list for the final sweep.
Two rules that make the cheap checks worth more than they look.
  • Mutation-test before trusting a green suite. Break the implementation deliberately and confirm the tests go red. This project keeps few tests on purpose, so one that cannot fail is worse than none. And verify the mutation actually applied — a mutation that silently fails to patch looks exactly like a blind test suite, and the second is the alarming one.
  • Prefer a mechanical check to a reviewer where the question is "does the artifact this task names exist and do what it says". Grepping paths, scripts, exported symbols and routes against the task text catches the same class of gap for a fraction of the cost.

Resolved decisions

Entries dated 2026-09-05 come from a review of P3 as built, against this plan and against architecture.html (the P3-review entry); those dated 2026-09-04 come from an adversarial review of the schema against canon and against SQLite itself, run before migration #1 was emitted (the hardening entry); those dated 2026-09-02 come from executing P0 against a real toolchain and the real topojson file; those dated 2026-09-01 come from the planning pass. Where one supersedes an earlier decision, the retraction is stated in the entry itself rather than deleting the history.

  1. Date precision — fuzzy dates, not brackets. (revised 2026-09-01; supersedes the bracket-sourced model.) Every event carries when_min / when_max (TEXT ISO-8601 UTC, when_max >= when_min) plus a closed when_precision ∈ {time, day, month, season, year, decade}. The author enters a precision and a value; the pair is derived from it (year 2036 → [2036-01-01T00:01:00.000Z, 2036-12-31T23:59:00.000Z]). when is a roll inside that interval, persisted and changed only by an explicit re-roll — that is what keeps node positions, arc endpoints and shared URLs stable across reloads. range_before_event_id / range_after_event_id are optional and narrow the interval; they never source it. This kills the circularity where L957 "2071: Enceladus reaches Etna" was to bracket L958 "Late 2071: Ines's first symptoms" — an event whose own when is itself a roll. Views render by precision: a year-precision event displays "2036", never a fabricated datetime; only time shows a clock. (2026-09-04 addition — two refinements, neither changing the model. The TEXT shape is now pinned and GLOB-checked: see below, and note this entry originally wrote its own interval without the .000Z. And the same render-by-precision rule now reaches the six non-event bounds that were storing a bare instant — the non-event-precision decision.)
  2. Events are points; extent lives elsewhere. (2026-09-01.) An event is a point in time. Anything with duration is a timeline of kind era / thread, or a project (which already has date_start / date_end). "2042 onward" is a thread; "HV V1–V3 '54–'70" is a project. The Tech Tree renders a multi-year programme as a project-linked lane span with its milestone events as nodes on it (P13.5).
  3. Rename chains. One Location per place. A rename is an event located there, linked to the event carrying the name it replaced by a renames relation. (2026-09-05 correction — this entry read "chained to the prior name", i.e. new → old, while the seed writes the location chain old → new and nothing rejects the reverse edge. renames is old → new: from is the superseded name, to the replacement. See the relation-direction decision.) No event.kind field — dropped as redundant with category + tags. (2026-09-01 addition:) location.superseded_by_location_id? records the identity chain (COPI → FOB Oasis → Camp Oasis → Oasis City → Star City). Views resolve to the canonical head, so "events located there" returns the whole history rather than a fifth of it. (2026-09-04 correction:) the chain is acyclic with one successor per row — not "strictly linear, no merges", which is how architecture §2.2 had it and which canon contradicts: COPI → FOB Oasis → Camp Oasis (L894, L898) and Disaster Ridge → Oasis City (L941) converge on one head, and the glossary calls Oasis City the fourth designation. Two rows naming the same successor is a legitimate merge, so superseded_by_location_id deliberately carries no UNIQUE constraint — only <> id and the write-time cycle check.
  4. Characters / Locations / Projects registry. First-class tables alongside events. Lifespan / project dates are plain date columns (not event refs). (2026-09-01 addition:) they are editable in-app — P12.3. Without that, the first event set anywhere the Bible did not name needs raw SQL.
  5. Era overlap. Events whose date falls in both an era and an adjacent era appear in both — by design.
  6. Era names and bounds. (2026-09-01.) The Bible's four era headings are used verbatim: "Pre-Big One", "North Korean War", "Black Fever Era", "Reconstruction Era". Their numeric bounds are authored modelling decisions, not canon: the glossary puts the Reconstruction Era at "beginning around 2047" while its first bullet is dated 2046, and the National Consolidation section is undated entirely. Seed them as "Black Fever Era (2042–2047), exact bounds authored, not canon", and let the overlap rule above absorb the 2046/2047 seam.
  7. Relations. Three types — precedes / partOf / renames. Stored once with a canonical direction; reverse views ("what succeeds X?") derived at query time. Tag overlap on create surfaces relation suggestions; user confirms. (2026-09-01 addition:) write-time validation — precedes from A to B requires A.when < B.when (P12.12).
  8. One app, four views. Unified shell — no separate apps. Existing map/ rebuilt as a view; the standalone folder goes away. (2026-09-01 addition:) it goes away through a gated migration, not a delete — P1.10 drain → P2.8 parity → P2.9 deletion, in its own revertible commit.
  9. Family Trees renderer. react-flow — gets pan / zoom / drag / minimap / connect-to-edit for free. (2026-09-01 addition:) the graph handed to d3-hierarchy contains synthetic union nodes. d3-hierarchy requires one parent per node, and the Castaneda sketch draws Lazaro→Adan and Ines→Adan. One union node per spouse-pair; children attach to the union; single parents attach directly (P14.2).
  10. Saves model. Every editable row carries save_id. Active save lives in the shell. Forking copies all per-save rows (FKs into global tables — tag, country — copied verbatim, never remapped). Replaces map/'s localStorage "projects" concept across the whole app. (2026-09-01 addition:) the in-save table list splits into authored (copied) and derived (recomputed, never copied). Pipeline outputs are derived — that is what stops a fork from producing rows pointing at the parent's sim_run. country_projection is not in that bucket: it is Shared / global (architecture §7.1), computed over real-world countries and save-independent, so it is never copied and never remapped — a third treatment, not the second. P6.2.1 files it correctly; this line did not. The verbatim-copy rule for global FKs is unchanged: a join table whose FK is global is copied verbatim under the identical rule.
  11. character_relation scope. v1 family-only (parent-of / sibling-of / spouse-of / clone-of). Stored once; symmetric types (spouse / sibling) use canonical ordering (lower id as from). Other types add later without schema change. (2026-09-01 addition:) sibling edges are derived from a common parent. A stored sibling-of row exists only for siblings whose parents are not modelled — never both, or the same pair renders twice.
  12. Map renderer. Plain d3-geo + SVG. react-simple-maps dropped. A 3D-globe view via react-globe.gl is parked as a future second map view (see architecture §9). (2026-09-01 addition — one gesture, one owner:) in orthographic, drag rotates the projection and the wheel changes projection.scale(); paths are recomputed and d3-zoom is not mounted. In every other projection, d3-zoom owns both gestures on the wrapping <g transform> and the projection is static. Country paths carry vector-effect: non-scaling-stroke so strokes do not thicken under the zoom transform.
  13. Selection model — glow is a selector, not stored state. (revised 2026-09-01; supersedes "setPrimary recomputes glow by following FKs".) useSelection holds a single primary ({type, id}) and setPrimary() sets primary only. glow is never written into the store: it is a memoized derived selector — selectGlow(primary, world, registry) — exposed to views as useGlow(). Computing it at set-time is correct exactly once — on a click, with the data already loaded — and wrong in the case that matters most: opening ?primary=character:char_lazaro restores primary during the first render, before the world data resolves, so a glow written then is empty forever and nothing ever recomputes it. As a selector, the empty first evaluation is simply superseded when the fetch lands. No flat per-type id fields. (architecture §4.2) (2026-09-02 revision — D-B, the signature:) the positional four-argument form selectGlow(primary, world.events, world.groupings, registry.locations) is retracted: it cannot compute three of architecture §6's rules. groupings carries no derivable information now that the membership join-table decision removed country_ids; the country and grouping rules need groupingOf; and a project primary's lead needs registry.projects. An ever-growing positional list would churn again, so the arguments are grouped one per source store: selectGlow(primary: Primary, world: Pick<WorldData, 'events' | 'groupingOf'>, registry: Pick<RegistryData, 'locations' | 'projects'>): Glow. useGlow() reads both stores and calls it — P0.8.6. What glow covers is the glow-scope decision.
  14. Tags global. tag has no save_id — one canonical list shared across saves so timeline membership rules stay stable across forks. event_tag assignments remain per-save. (2026-09-01 addition:) a canonical vocabulary of ~20–30 tags is seeded (P3.1) before any event is tagged, tagging is an explicit step of the event seed, and a global tag cannot be deleted while referenced (refuse or soft-delete). A per-save tag vocabulary is explicitly out of scope for v1.
  15. URL state. primary + active save + filters all serialize to URL search params at the shell level — shareable, reload-restorable. glow is derived on load. Camera / viewport is not in the URL; it lives in the per-view back/forward stack (P8.6).
  16. Closed enums. event.category ∈ {tech, political, military, disaster, scientific, cultural, personal} — (2026-09-01:) project dropped, it duplicated the project_id FK. tech means an artifact or capability ships; scientific means a result is established. The Tech Tree reads only category='tech', so a wrong pick silently deletes a node. event.tech_lane ∈ {energy, propulsion, computing, neural, biomedical, megastructure} (only when category=tech). event.when_precision ∈ {time, day, month, season, year, decade}. timeline.kind ∈ {era, thread, cluster}. country.geometry_source ∈ {feature, derived}.
  17. Groupings — membership is a join table. (revised 2026-09-01; this RETRACTS the earlier decision recorded as "a grouping carries its members as a country_ids jsonb array — no grouping_country join table".) grouping (id, save_id, name, color) with country_ids removed; grouping_country (save_id, grouping_id, country_id) with PRIMARY KEY (save_id, country_id). The PK enforces the partition — one grouping per country per save. Verified: all 237 codes across the existing 103 groups appear in exactly one group, zero duplicates; that invariant is unenforceable in a jsonb array. An "independent nation" is a country with no row — the 74 synthesized independents in the exported file are a projection of country, built at export time by map/src/App.jsx:146-155 with a hardcoded slate color and an independent: true flag no schema has. They are not seeded. Fork copies grouping_country verbatim: it is per-save and country_id points into a global table, so the existing verbatim-copy rule survives word for word.
  18. Country key — total over the author's own data. (revised 2026-09-01; supersedes "canonical country id = ISO 3166-1 numeric".) country.id is TEXT: a zero-padded 3-char ISO numeric where one exists ("004", "250"), and a namespaced synthetic id otherwise ("x:GUF", "x:XKX"). Never an INTEGER — 4 != "004". iso_numeric? and alpha3? are nullable display/debug columns; name (not default_name) is the default real-world name, sourced from the topojson feature's properties.name; geometry_source ∈ {feature, derived}. Why: data/iso-numeric-to-alpha3.json contains "GUF": "GUF" and "undefined": "SOL" and both are live members of data/map_saves/lifestream_map_v1.json; world-atlas bundles French Guiana inside France's 250; Natural Earth gives Kosovo / N. Cyprus / Somaliland the id -99. A pure-ISO-numeric PK cannot represent any of them. The France→French-Guiana split (map/src/components/Map.jsx:27-45) is data-layer logic, not an app hack: it lands in shared/src/geo/deriveFeatures.ts, runs at topojson load, and produces the geometry_source='derived' rows.
  19. Simulation chain — schema now, subsystem deferred. (revised 2026-09-01; the route reservation and modular-stage design are unchanged.) The economic/epidemic pipelines live under server/src/services/simulation/ (route /api/simulation), not megacorp — the megacorp list is just the chain's last step. Order: project per-country → BF sim → combine → classify. Modular: each stage independently runnable (simulate <stage|all> / POST /api/simulation/<stage>), handing off only through persisted tables. What changes: the six pipeline tables land in migration #1 (P1.5) rather than waiting, because their primary keys are irreversible and the plan has no migration story after #1. The run_id in those PKs is the only run machinery bought now; the active-run pointer, staleness evaluation, retention/pruning and DAG orchestration stay deferred. Rationale: the PK is one irreversible line; the harness is a reversible subsystem — buy the cheap irreversible thing, defer the expensive reversible one. (2026-09-02 — one of the six PKs recorded here is superseded: nation_horizontal shipped as (save_id, run_id, grouping_id) and is now (save_id, run_id, country_id, horizontal) — the trailing horizontal was always in the schema and was simply missing from the plan's prose until 2026-09-04. See the nation_horizontal re-key. grouping_metrics keeps grouping_id — the combine stage is defined over groupings either way — and the other four are untouched.)
  20. Canonical time scale. (2026-09-01.) The event stratum's d3.scaleTime is canonical. All cross-view and cross-jump math — camera fly-to targets, the Tech Tree's shared X axis, viewport clamping — uses it. Other strata render via a z-dependent multiplier applied at draw time only, never in the data model. This resolves the collision between per-stratum time scales, the single world scale, the viewport clamp, the fly-to target, and the Tech Tree's "same scale as the Corridor" claim. Every task that does positional math cites this entry. (2026-09-05 — the origin becomes a constant:) "one scale" was aspirational while createTimeScale(earliest) took its origin from whatever corpus a view held — the Corridor's min(when) and a category='tech' Tech Tree's differ by 144.7 world units against a ~66-unit pane, so a cross-jump landed ~2.2 screens off with no error in either view. The origin is now CORRIDOR_START, a module constant, and TIME_SCALE is a single per-process object every view imports (P4.2.1, architecture §5.2). A re-seed no longer moves the world, so serialized camera x and saved viewports survive it.
  21. Depth camera: continuous, no snap. (2026-09-01.) Vertical scroll moves camera Z continuously. Snapping to strata means the camera never rests in the blended region, which degrades the cross-fade to a transition animation and contradicts the stated goal of moving through depth.
  22. Node vertical offset is a deterministic hash. (2026-09-01.) An event node's y is hash(event.id) folded into its category band — never a random jitter computed at mount. Random y moves nodes on every reload and breaks fly-to targets, the viewport stack, arc endpoints and shared URLs.
  23. Export IR. (2026-09-01.) The IR gains inline formatting — type Inline = string | Array<string | {b|i|code} | {link:{href,text}}>, paragraph.content: Inline, type Cell = Inline | Block[] — plus a single { type:'image', src?, alt?, caption?, mermaid?, svg? } block (P15.1.2) — one block shape carrying mermaid? | svg? | src?, not three, so a renderer degrades rather than a builder branching. character.portrait_path has nowhere to render without it. Builders always emit the richest block; renderers degrade. "When the export target supports SVG…" is removed: a builder that branches on target capability restores the exact N×M dimension the IR exists to remove. Diagram export needs a browser — react-flow renders HTML divs, so there is no SVG to dump and a headless browser is ruled out; v1 ships the family export list-only, with POST /api/export/asset reserved for a client-rendered capture.

Every post-seed schema change ships a drizzle migration plus a backfill script. db:seed is idempotent — upsert by natural key — and never destructive. db:reset refuses unless a dump newer than the last write exists. npm run db:dump writes data/save_dumps/<save>.json and must exist and be part of the routine before the editing phase, because in-app editing makes the gitignored SQLite file the only home for authored content. (2026-09-04 — made executable:) the three rules are now three commands — scripts/db-check-migrations.mjs, scripts/db-check-seed.mjs, and the freshness gate inside scripts/db-reset.mjs — over shared guards in scripts/lib/, and the reset gate ships ahead of its own precondition: with no db:dump yet it refuses with no-tooling and --force is the only way through, rather than waving the destructive path past until P11. See P1.7.

Exactly four targeted tests, no coverage push: the country import (P1.9), resolveTimeline() DAG recursion + cycle detection (P3.5), the fork remap manifest (P6.2), and rollDate (P1.8). (2026-09-02 addition:) two of the four are database-backed and therefore blocked on the test-fixture decision and its createDb(url) requirement.
  26. Route module → URL prefix. (2026-09-02 — D-A.) The nine files under server/src/routes/ are a file layout, not a URL layout. Mounting each at its namesake prefix would contradict architecture §5.1/§5.2, which already specifies the URLs — the architecture wins, it already decided — so a module may own more than one prefix and there is no /api/registry prefix at all. The mapping, fixed here so no later task re-derives it: registry.ts → /api/characters, /api/locations, /api/projects, /api/character-relations; map.ts → /api/map/countries and /api/map/groupings (the reads) plus top-level /api/groupings/* and /api/country-overrides/* (the writes); the other seven mount at their namesake prefix — /api/events, /api/timelines, /api/relations, /api/tags, /api/saves, /api/simulation, /api/export. Mounted in P0.3.6; consumed by P3.6.4.
  27. Glow scope — a location primary, and no rename-chain walk. (2026-09-02 — D-C, D-D.) Two gaps in architecture §6's cross-view linking table, both closed deliberately. (D-C) 'location' is a member of the Primary union but the table had no row for it: a location glows the events sited there, plus itself — one FK hop, which is what the table's own "driven by the foreign keys" sentence implies. Nothing beyond that is invented. (D-D) Glow does not walk superseded_by_location_id: an event pointing at a superseded location does not glow through to the canonical head, even though the byLocation membership predicate does resolve the chain — on both sides of the comparison since 2026-09-05 (the both-sides decision), which widens the gap between the two behaviours without changing why it is there. The asymmetry is intentional — membership says what a timeline contains and must survive a rename; glow says what the user just clicked and stays literal — and it is written down here precisely because the two halves look like a bug when read side by side.
  28. Wire format is camelCase. (2026-09-02 — D-E.) SQL columns are snake_case (when_min, location_id, save_id) — that is how every schema task in P1 names them, and how the emitted migration reads. Everything above the drizzle boundary is camelCase: JSON response bodies, the shared TS types, the client stores and props. Drizzle's inferred types already do this, so the schema file is the only conversion point and no hand-written mapper exists. Stated once, here, so the read APIs in P1.12 and P3.6 do not ship snake_case payloads and churn the client types a phase later.
  29. Test database fixture — :memory:, fresh per test file. (2026-09-02 — D-F.) A spec that needs a database opens its own better-sqlite3 :memory: connection in setup and applies the migrations through drizzle's better-sqlite3 migrator. Vitest's default forks pool already isolates one file from another, so per-file freshness costs nothing; keep forks — better-sqlite3 is a native module and the threads pool goes badly with it. The binding constraint: none of this is writable while server/src/db/index.ts is a module-level singleton hard-wired to data/lifestream.db, which is exactly what P0.9 shipped. P1.6.3 turns it into a createDb(url) factory; until it does, the country-import (P1.9.5) and fork-remap (P6.2.8) tests cannot be written without a refactor — half the plan's entire test budget.
  30. Toolchain facts, recorded on first contact. (2026-09-02; discovered by executing P0 for real.) Written down so nobody re-discovers them. TypeScript is 6.0.3: baseUrl is a hard error (TS5101), not a warning, so tsconfig.base.json declares none and its paths are config-relative — "@shared/*": ["./shared/src/*"].     Nothing in the plan covered this, which is why migration #1 had to be right by luck. Write it down as an executable rule, in docs/ and in the scripts themselves — see the migration/backup policy. Each of the three rules below is a command that exits non-zero when the rule is broken; architecture §7.4 states the same three from the design side. The guards they share live in scripts/lib/ — repo.mjs (the import.meta.url anchor plus the is-this-really-the-repo check), backup.mjs (the dump-freshness gate), fingerprint.mjs (content hashing) — so that no script re-implements one and gets it subtly wrong.

    • P1.7.1Every post-seed schema change ships a drizzle migration plus a backfill script. A migration with no backfill is not a complete change. Enforced by node scripts/db-check-migrations.mjs, which reads migrations/meta/_journal.json and requires, for every migration past the baseline, exactly one of scripts/backfills/<tag>.ts (the backfill — .mts/.mjs/.js/.sql also accepted) or scripts/backfills/<tag>.data-free.md (the written waiver §7.4 allows when a change is provably data-free). Never both, never neither, and the waiver must be at least 40 characters of actual argument — "no data." fails, because the rule is that the commit says so, not that a file exists. It also catches the two ways the migration set drifts from itself: a journal entry with no .sql, and a hand-added .sql the journal does not list, which db:migrate would silently never run. Migration #1 (P1.6) is the baseline and exempt by construction: it created the schema, so no rows existed to move.
    • P1.7.2db:seed is idempotent — upsert by natural key (country id, tag name, save name, grouping name within a save) — and never destructive. Running it twice is a no-op; running it after edits does not clobber them. Enforced by node scripts/db-check-seed.mjs, in two halves because neither alone is enough. Static: the seed sources (scripts/seed.ts and server/src/seed/**) are scanned — comments stripped first, or the sentence a careful author writes about never running DELETE FROM reports itself as a violation — for DROP, DELETE FROM, TRUNCATE and drizzle's .delete(, plus evidence that an upsert exists at all. Dynamic: it takes a SQLite-level snapshot of the database, runs the seed against the snapshot twice, and compares an order-independent per-table content hash of the two runs — raw bytes are useless here, because SQLite rewrites pages on an upsert that changes nothing and, conversely, leaves the file byte-identical when the upserted values already match. Three exit codes, and the third is the point: 0 compliant · 1 violation · 2 inconclusive. A run that could not verify idempotence — the seed is still a stub, or it exited non-zero, or it wrote nothing to an empty database — must never read as a pass.
    • P1.7.3db:reset refuses unless a dump newer than the last write exists (P11). Override requires an explicit --force. The gate ships now rather than with the dump tooling, and degrades by refusing rather than by warning — a guard that passes silently while its own precondition is unimplementable reads as protection and is not. Five states: no-database (nothing to lose, so proceed) · fresh (proceed) · stale · no-dumps · no-tooling. The last is today's, since db:dump does not exist yet and therefore no dump can be fresh; the refusal says exactly that and names the override, and the day P11.1 adds the script the same code starts asking for a dump instead, untouched. --force overrides the freshness gate only — never the repo-identity check, which has no legitimate override — and an unknown flag is a hard error, because a mistyped --force must never read as "not forced". --dry-run lists the targets and deletes nothing. The corollary worth stating: the seed can add and update but never delete, so a bullet removed from the Bible is caught by the drift guard and reconciled by the author, never by a silent row drop.

What cannot be generated from the doc, and should not be

The Bible supplies prose and a date phrase. It does not say whether a bullet is military or political, whether “Late 2071” is season precision, which stage of a rename chain a location is at, who acted in it and in what role, or whether one compound bullet is two events. That is interpretation, and it lives in the authored tables of P5 under the drift guard. “Generated from the doc” means the facts are parsed and never retyped, not that the readings are inferred.

P7 Time Corridor II — multi-stratum (depth + parallax)

Goal: vertical scroll moves the camera through depth, continuously. Eras / threads / clusters / events live on different Z layers; only the focused stratum is bright, and the layers between cross-fade. The event stratum's d3.scaleTime from P4.2.1 is canonical. Camera fly-to targets, the Tech Tree's shared X axis and viewport clamping all use it. Other strata render via a z-dependent multiplier applied at draw time only. Nothing writes a per-stratum coordinate back into layout data, and nothing outside this phase ever sees a non-canonical x. The contract is stated normatively in architecture §5.2 — this phase cites it and does not define it, so an edit to §5.2 propagates here rather than leaving two divergent statements.   • P7.4Derive cluster nodes — with actual parameters SPECIFIED

DIMMED_EMISSIVE is 0.18 and DEFAULT_BLOOM.luminanceThreshold is 0.25, so a dimmed normal node lands at 0.099 and provably cannot bloom, while a dimmed glow node lands at 0.270 and a dimmed focused one at 0.432 — both still bloom, the second at 1.7× the threshold. That may well be right: a filtered-out glow node is still a search hit, and a filtered-out focused node is the reader's own selection (§6), which is worse to lose than to keep legible. But it contradicts what the constant's comment used to claim, and nothing exercises dimmed until this task, so P4 recorded the arithmetic rather than guessing. Decide it here, with filters actually on screen. Taking focused under the threshold needs DIMMED_EMISSIVE below 0.104; taking glow under needs below 0.167. tests/eventNodeVisual.test.ts pins all three products against the real threshold, so moving either number forces the question rather than letting it drift.
